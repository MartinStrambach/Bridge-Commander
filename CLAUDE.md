# Bridge Commander - Claude Code Guide

macOS app for managing Git repositories and worktrees. Built with SwiftUI + TCA (Composable Architecture).

## Tech Stack
- Swift 6.0+
- SwiftUI
- Composable Architecture (TCA)
- macOS 26.0+
- Xcode 26.2+

## Project Structure

The app is modularized into SPM packages under `Packages/`, with the thin app target in `BridgeCommander/`.

```
BridgeCommander/          # App entry point (BridgeCommanderApp.swift), Sparkle updater
Packages/
  ProcessExecution/       # Shelling out to external processes (ProcessRunner)
  GitCore/                # Git operations and models
  GitHosting/             # GitHub/GitLab pull request + pipeline services
  AppUI/                  # Shared UI components and diff viewer (+ DiffModelMapping target)
  Settings/               # Settings state, view, and app-wide keys
  ToolsIntegration/       # Xcode, YouTrack, Android Studio, Terminal, Claude Code
  TerminalFeature/        # Embedded terminal (session, view, store)
  ActionButtons/          # Android Studio button Reducer+View pair
  GitActionsMenu/         # Git actions menu (push/pull/fetch/stash/merge/checkout default/discard/abort)
  YouTrackMenu/           # YouTrack ticket menu (move to a reachable state)
  GitGraphFeature/        # Commit graph view + selected commit's diff
  StagingFeature/         # File staging panel (detail view, diff, commit)
  RepositoryFeature/      # Repository list/row views and reducers (top-level feature)
```

### App Target

- Updates come from Sparkle (the app target's only direct package besides TCA). `BridgeCommanderApp` owns the `SPUStandardUpdaterController`; `CheckForUpdatesView` is the "Check for Updates…" app-menu item. The updater is started only in Release builds: a Debug build runs out of DerivedData, and installing an update there would replace the build being worked on
- Settings ▸ Updates (`UpdateSettingsView`) toggles automatic checks and automatic download/install, with a Check Now button. They read and write `SPUUpdater`'s own properties (`automaticallyChecksForUpdates`, `automaticallyDownloadsUpdates`), which Sparkle persists itself — the same preferences its second-launch prompt and the update dialog's checkbox set, so they are not mirrored in `SettingsReducer`. Both views observe them through `UpdaterViewModel` (KVO). The view lives in the app target and is handed to `SettingsView` as its `updates` content, keeping the Settings package free of a Sparkle dependency; that makes `SettingsView` generic, so its former static stored properties sit at file scope. The download toggle is disabled while `allowsAutomaticUpdates` is false (automatic checks off), and the whole section in Debug builds
- Debug builds use their own bundle identifier, `com.bridgecommander.BridgeCommander.debug` (display name "Bridge Commander Debug"), so they keep separate user defaults and Application Support data (`Bundle.main.bundleIdentifier` names the folder) — a debug run's saved terminal tabs, tracked repositories and settings never reach the release app. The cost is a separate set of TCC grants (Accessibility, Automation, notifications) for the debug build. Its icon is `AppIconDebug` (the app icon with a red "DEBUG" corner ribbon), generated from `AppIcon` by `scripts/make-debug-icon.py` — rerun it after changing the icon
- `BridgeCommander/Info.plist` is merged over the generated plist (`GENERATE_INFOPLIST_FILE` plus `INFOPLIST_FILE`) and holds only keys with no `INFOPLIST_KEY_` setting: `SUFeedURL`, `SUPublicEDKey` and `SUScheduledCheckInterval` (43200 s = 12 hours; Sparkle's default is a day). Anything else in it would override the generated value. It is excluded from the synchronized folder's resources. `CFBundleVersion` is `$(MARKETING_VERSION)` because Sparkle compares versions by it
- The feed is an `appcast.xml` attached to each GitHub release by `make publish` (`scripts/make-appcast.sh`; see RELEASE.md)

### Package Details

**GitCore** — git primitives and data model
- `ScannedRepository` — core model (path, name, branch, worktree flags, change counts)
- `GitService` — main git client (DI-injected as `GitClient`)
- `GitStatusDetector` — `getBranchAndChanges` returns all status in one git call
- `GitStagingClient` / `GitStagingHelper` — staging operations
- `GitCommitDiffClient` / `GitCommitDiffHelper` — read-only: what a single commit changed (`git show`). Merges are diffed against the first parent (`--first-parent`), because git prints no diff for a merge otherwise; a root commit shows every file as an addition. Nothing here writes, so browsing commits never moves HEAD, the index or the working tree
- `GitCommitActionHelper` / `GitCommitActionClient` — the commit graph's write actions: cherry-pick and revert (`apply`, one `GitSequencerOperation` type for both; a merge is taken with `-m 1`, the first-parent side the graph's diff shows), `abort`, detached checkout, checking out a remote branch's local namesake (the existing one, else `checkout -b <name> --track`), and branch creation. Stopping on conflicts is an outcome (`GitSequencerOutcome.conflicts`), not an error, and leaves `CHERRY_PICK_HEAD`/`REVERT_HEAD` for the user to commit or abort. Stopping *without* conflicts (the commit's changes are already on the branch, so the result is empty) is aborted before throwing, so a failure never leaves a sequencer in progress. Covered against a real temp repository in `GitCommitActionHelperTests`
- `GitWorktreeCreator.createWorktree(fetching:branchCandidates:…)` adds a worktree for a fork's PR/MR: fetches only that head ref from `origin` and checks it out on the PR's own branch name (which the row's PR lookup finds it by), or `<fork owner>/<branch>` when that is taken. It reuses an existing branch only if it equals the head, or if an earlier call made it for the same ref — marked in `branch.<name>.bridgeCommanderPullRequest`, which `git branch -d/-m` carry with the branch. Ancestry alone is not enough: the PR's base (a fork's PR often comes from `main`) is an ancestor of its head too, and would have been fast-forwarded onto it. Such a branch is fast-forwarded when behind and kept when it has local commits. No upstream is set, so the PR's commits count as unpushed. Covered against a real origin + clone in `GitWorktreeCreatorForkTests`
- `GitWorktreeCreator.createWorktree(branchName:startPoint:…)` adds a worktree on a new branch at any revision, with no fetch. It places the folder relative to the *main* repository (`GitDirectoryResolver.resolveMainRepositoryPath`), so a worktree made from a linked worktree's graph lands beside the others rather than inside it
- `GitRepositoryWatcherClient` (`GitRepositoryWatcher`, `GitChangeClassifier`, `FileSystemEventStream`) — reports changes on disk to the listed repositories as `GitRepositoryChange`s (`.status`, `.stash`, `.worktreeList`), so rows update without the periodic refresh. One `FSEventStream` (per-file events, 0.3 s latency) over every working tree and common git directory. FSEvents, not a `DispatchSource` per file: git replaces `HEAD`/`index`/refs by renaming a `.lock` file over them, so a descriptor watch goes dead after the first write. Inside git directories only the per-worktree `HEAD`, `index`, `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-*`, `config.worktree` (that worktree), the shared `refs/`, `packed-refs` and `config` (every worktree of the repository; `refs/stash` as `.stash`; `config` because `git branch -u` writes only there yet moves the upstream) and a created/removed `worktrees/<name>` or a rewritten `worktrees/<name>/gitdir` (`.worktreeList` — `git worktree move` changes nothing else) count — `objects/`, `logs/` and `*.lock` are churn. A reftable repository (`--ref-format=reftable`, git 3.0's default) keeps every ref, `HEAD` included, in `reftable/` and never writes `refs/` or `HEAD`; its commit point `reftable/tables.list` counts as `.status` + `.stash` for every worktree (which ref moved cannot be told from the path), and `worktrees/<name>/reftable/tables.list` as that worktree's own `HEAD`. Working tree paths are batched through `git check-ignore`, so a build writing into ignored output costs one cheap process per batch instead of a `git status`. Paths are compared canonically (`realpath`, which keeps `/private/var` the way FSEvents reports it); a changed path belongs to the innermost working tree. The live stream never finishes by itself: a path that is not a repository yet (a worktree whose `.git` file was not written when the scan listed it) is re-resolved every `retryInterval` (30 s), the stream restarting only when the set it can watch changes, and a stream FSEvents refuses is retried on the same interval — the list restarts a watch only when its rows change, so without this such a row stayed unwatched. Its `testValue` is a stream that finishes at once, not unimplemented: every scan starts a watch
- `GitStatusDetector` runs `git --no-optional-locks status`. Without the flag git writes refreshed stat data back to `.git/index`, which the watcher reacts to — every refresh would schedule the next
- `GitLogHelper` / `GitLogClient` — the commit graph's `git log` (all branches, remotes, tags and HEAD, topo order), optionally narrowed by a `GitLogSearch` (field + trimmed query, nil when blank)
- `GitDiffHunkParser` — shared unified-diff → `DiffHunk` parsing (line numbering + `InlineDiffHighlighter`), used by both the staging and commit diff paths
- `ProcessRunner` — shells out to git via `runGit()`
- Helpers: `GitWorktreeScanner`, `GitWorktreeCreator`, `GitBranchNameSanitizer` (whitespace → underscores for typed branch names; leading whitespace dropped, so a name of only spaces stays empty), `GitWorktreeRemover`, `GitMergeDetector`, `GitBranchDetector`, `GitDefaultBranchDetector`, `GitBranchListHelper`, `GitPullHelper`, `GitPushHelper`, `GitFetchHelper`, `GitMergeHelper`, `GitCheckoutHelper`, `GitAbortMergeHelper`, `GitStashHelper`
- `GitImageDiffLoader` / `ImageDiffSides` / `ImageFileDetector` — load both versions of a changed image (`git cat-file blob`) so a diff view can render them instead of a binary placeholder. `ImageDiffSource.revision(revision:path:)` is the general side (`<rev>:<path>`); `.head(path:)` is sugar for `HEAD`. `resolve(for:isStaged:)` covers the staging comparisons, `resolve(for:commitHash:)` a commit against its first parent

**AppUI** — shared UI components
- `ActionButton`, `ToolButton`, `HeaderButton`, `HunkActionButton`
- `DiffViewer`, `DiffLineView`, `HunkCard` (`HunkHeaderView`, `HunkFooterView`, `hunkCardRow()`), `ImageDiffView` — diff display (images render side by side as Before/After; pinch zooms toward the pointer, drag pans when zoomed, double-click resets. Both panes share one `ImageZoom`, whose offset is a fraction of each image's fitted size rather than points, so Before and After stay aligned even when drawn at different sizes). `ZoomableImageLayerView` draws the image as a `CALayer`'s contents with the zoom as the layer's transform, and handles pinch, pan and double-click itself in AppKit (`magnify`/`mouseDown`/`mouseDragged`, with `clickCount == 2` for the reset). Not as SwiftUI gestures: a `.onTapGesture(count: 2)` beside a `DragGesture` made AppKit hold the drag's events back waiting for a second click and deliver them in bursts of ~25 every ~0.6 s (measured 2026-09-29), so panning jumped while pinching stayed smooth
- `DiffViewer` renders diff lines with a `List`, not a `ScrollView` + `LazyVStack`. A lazy stack reports its content's height as its own ideal height, so a large diff handed the enclosing sheet an ideal size of ~10⁶ pt that changed every time more rows were measured; the sheet re-measured, the stack re-estimated, and the main thread spun in `LazyLayoutViewCache.updateItemPhases` / `LazyStack.measureEstimates` for minutes (hang reports 2026-09-06 and 2026-09-07 — flattening the stack in v0.6.7 did not help, the signature was identical). `List` is `NSTableView`-backed: rows recycle and its ideal size is 0×0 regardless of row count
- Hunk header, lines and footer are emitted as sibling rows of one `List`, deliberately not as a `Section` — a plain-style `List` pins section headers, which would make hunk headers sticky. Rows need `.listRowInsets(EdgeInsets())` and `.listRowSeparator(.hidden)` (see `diffListRow()`), plus `defaultMinListRowHeight` of 1 so content height wins and no gap opens in the card's side borders. Do not add `.listRowBackground` — it costs ~40% of scroll time and changes nothing visually
- `DiffViewer` has two inits: the staging one takes the hunk stage/unstage/discard closures, `init(diff:)` is read-only and renders hunk headers without action buttons. `FileChangeRow` likewise has `init(file:)` for a row with no staging checkbox
- `GitOperationProgressView`, `BannerView`, `EmptyStateView`, `ScrollableErrorAlertView`
- `View.windowTitleBarArea()` — the main window is `.hiddenTitleBar`, so the app's own top bars (list header, terminal toolbar, terminal sidebar header) stand in for the title bar: a double-click there zooms/minimizes per the system's title bar setting (`AppleActionOnDoubleClick`), a drag moves the window. SwiftUI gestures (`onTapGesture(count: 2)` + `WindowDragGesture`), not an `NSView` overriding `mouseDown`: the hosting view routes clicks itself and reached a background `NSView` only over part of the bar. Apply it *before* any `.background(Color…)`, or the color sits in front and takes the clicks
- `UIFontScale` — the app's text scaling. macOS ignores `dynamicTypeSize` (a text style renders at one size whatever it is set to — checked 2026-10-06), so views write **`.scaledFont(.caption)`** / `.scaledFont(.body, design: .monospaced)` / `.scaledFont(size: 12)` instead of `.font(...)`; the modifier multiplies the style's macOS point size by the `uiFontScale` environment value. At scale 1 it returns the text style itself, so the default renders exactly as before. `View.uiFontScale(_:)` sets the scale plus a scaled body font for text with none of its own (no font at all at scale 1); it is one modifier chain rather than an `if`, because a branch at the root would reset every window's state whenever the setting crossed 1. Keep `.font(.system(size:))` only where the glyph sits in a fixed-size frame (the merge badge in `RepositoryIcon`, `HeaderButton`, avatar initials). `GitGraphRowView.rowHeight(scale:)` grows with it
- Controls AppKit draws ignore an inherited font (measured 2026-10-06 with `NSHostingView.fittingSize`), so the root font does not reach them: push and bordered buttons only take a font set *inside* their label, at every control size — use **`.buttonStyle(.scaledBordered)` / `.scaledBorderedProminent` / `.scaledAutomatic`** (`ScaledButtonStyle`) instead of `.bordered` / `.borderedProminent` / no style on a text button; it puts the control size's title size × scale in the label, and passes the native button through untouched at scale 1. A `.borderlessButton` menu's label is flattened by AppKit, which drops `scaledFont`'s environment read and keeps only a literal font, so those views read `@Environment(\.uiFontScale)` and write `.font(.system(size: 12 * uiFontScale))` on the label `Text` (`GitActionsMenuView`, `TuistButtonView`, `YouTrackButtonView`). Plain/borderless buttons, toggles, steppers and text fields follow the inherited font as-is; a menu-style `Picker`'s popup title and segmented pickers stay at the system size whatever is set
- `FileChangeRow`, `SectionHeader`, `RepositoryIcon`
- The **`DiffModelMapping`** target (same package, separate product) holds the `GitCore.*.toAppUI()` conversions. It is where AppUI and GitCore meet, so the `AppUI` target itself stays free of any git dependency and the mapping is not duplicated per feature. Import it alongside `AppUI` wherever a GitCore diff is rendered

**Settings**
- `SettingsReducer` + `SettingsView`. The view is a fixed-width sidebar `List` beside a scrolling page — not a `NavigationSplitView`, which in the Settings window ignored `navigationSplitViewColumnWidth` and opened the sidebar at 144 pt, cutting the longer titles. The sidebar lists `SettingsCategory` pages (General, Accounts, Repository Groups, Branches & Worktrees, Terminal — the built-in one, External Apps — terminal app / Claude Code / Android Studio buttons, Tuist, Updates), each page a stack of `SettingsSection` cards. The page last shown is remembered in `@AppStorage("settings.selectedCategory")`; the sidebar's selection binding ignores nil writes so a click on empty space keeps the page
- `AppSettings` keys via `SharedKeys`
- `PeriodicRefreshInterval`, `ClaudeStatusDetection`, `TerminalColorTheme`, `TerminalOpeningBehavior`, `TuistCacheType`, `RepoGroupSettings`
- `TerminalFontSize` — the built-in terminal's point size (8–32, default 13 = `NSFont.systemFontSize`, which is what SwiftTerm's `FontSet.defaultFont` asks for, so an untouched install renders as it did before the setting existed). Stored as a bare `Double` and clamped on every write, including the one that comes back from user defaults: SwiftTerm divides the pane width by the cell width to get its column count, so a zero or negative size is not a value it can survive. Written by the Settings stepper and by ⌘+/⌘−/⌘0 (`TerminalLayoutReducer`'s zoom actions)
- `UIFontSize` — the app's own text size (Settings ▸ General ▸ Appearance), stored as a body point size (10–20, default 13 = macOS body, scale 1) under `uiFontSize`; every text style scales by `size / 13`. `View.appUIFontSize()` reads the setting and applies AppUI's `uiFontScale`; the app target puts it on the root of both scenes. Separate from the terminal's `TerminalFontSize`
- `TerminalFontFamily` — the built-in terminal's typeface, stored as the bare font name `NSFont(name:size:)` takes, with `""` meaning `NSFont.monospacedSystemFont` (what SwiftTerm used before the setting existed, and the only way to say "follow the system" — the system monospaced face has no stable public name). `resolve(name:size:)` falls back to that face for any name that no longer resolves, since the name comes from user defaults and a font can be uninstalled. The picker lists only families with a fixed-pitch member (`availableMonospacedFamilies()`): a proportional face turns SwiftTerm's character grid ragged. `TerminalPanelView` resolves name + size into one `NSFont` and hands it to `TerminalContainerRepresentable`, so TerminalFeature needs no Settings dependency
- `TerminalProfileImporter` / `TerminalProfile` / `TerminalProfileImportClient` — import Terminal.app color profiles, either from an exported `.terminal` file or from Terminal's own settings in one tap. Both sources are property lists holding the same profile dictionaries; the colors in them are **`NSKeyedArchiver`-encoded `NSColor` objects**, not hex strings, so each one is `NSKeyedUnarchiver.unarchivedObject(ofClass: NSColor.self,…)` then `usingColorSpace(.sRGB)`. Converting first is not optional: Apple's bundled profiles store colors in Generic RGB *and* Generic Gray, and reading `redComponent` off a gray color raises. Alpha is dropped (the "Clear" profiles are 0.85–0.95 translucent; SwiftTerm's color type has no alpha). Reading Terminal's settings goes through `UserDefaults.persistentDomain(forName: "com.apple.Terminal")` — it sees unflushed values, and works only because the app is unsandboxed
- Only 2 of Terminal's 12 bundled profiles define ANSI colors at all ("Basic", "Pro" and most others set just a text and background color), so `TerminalProfile.ansi` is optional rather than defaulted — `nil` means "keep SwiftTerm's default palette", which *is* Terminal's. A palette is all sixteen or none: SwiftTerm ignores any array that is not exactly 16 long, so a partial one would silently leave the previous theme's colors installed
- A profile's `Font` key is an encoded `NSFont` and is imported too, into `TerminalProfile.font` (name + size), applied to the global font settings when that profile is picked as the theme (`SettingsReducer.adoptProfileFont`) — font is part of a profile in Terminal.app, so a theme switch overwrites a hand-picked font the same way it overwrites the colors. It must **not** be decoded with `unarchivedObject(ofClass: NSFont.self,…)` the way the colors are: when the archived face is not installed AppKit substitutes one and the name is lost, and Terminal's own profiles name `SFMonoTerminal-Regular`, which ships *inside* Terminal.app and is not registered system-wide — so unarchiving it yields `.AppleSystemUIFont`, a proportional face, and the import silently records the wrong font. `TerminalProfileImporter.font(from:)` instead maps the archived class name `NSFont` onto the decode-only `ArchivedFont` stub (`setClass(_:forClassName:)`) and reads `NSName`/`NSSize` as written, with `decodingFailurePolicy = .setErrorAndReturn` so a non-font value under that key returns nil rather than raising. Applying is split accordingly: the size always applies, the family only when `NSFont(name:size:)` resolves it, and the import alert names any profile whose font it could not load
- An imported profile's `CursorColor` and `SelectionColor` ride along in `ResolvedTerminalTheme` (`nil` for built-in themes and for profiles that omit them, meaning "keep SwiftTerm's default") and are assigned in `TerminalViewStore.view` after `installColors`, onto `caretColor` and `selectedTextBackgroundColor`. Setting the selection background **must** set `selectedTextForegroundColor` with it: SwiftTerm does not tint the selection, it replaces the foreground of every selected cell with that color, which defaults to black — readable against its own teal default and invisible against the dark selection colors most Terminal profiles ship. It is set to the profile's own text color, the color whose author already judged the selection color to work behind it
- `TerminalThemeSelection` — `.builtIn` or `.imported`. A built-in case's raw value is the bare `TerminalColorTheme` raw value, unprefixed, so the setting this type replaced migrates itself: an existing `"dracula"` in user defaults still reads back as `.builtIn(.dracula)`. `resolve(profiles:)` falls back to the default theme when a selection names a deleted profile

**ToolsIntegration** — external tool services
- `ServiceProtocols` — protocol definitions
- `XcodeService`, `YouTrackService`, `LastOpenedDirectoryService`
- `TerminalLauncher`, `ClaudeCodeLauncher`, `AndroidStudioLauncher`
- `XcodeProjectDetector`, `XcodeProjectGenerator`, `XcodeDerivedDataHelper`
- `TuistCommandHelper`, `BranchNameFormatter`, `FileOpener`, `PermissionChecker`
- `BranchNameFormatter` goes both ways: `format` turns a branch into the row's display text, `branchName(ticketId:summary:template:)` names a branch after a YouTrack ticket. The template (`ticketBranchNameTemplate`, `{ticket}`/`{summary}` placeholders) defaults to `{summary}_{ticket}`, the shape `format` reads back as the bare summary; the summary becomes a lowercase ASCII slug with diacritics folded (Czech summaries stay readable), cut at a word boundary at 50 characters
- `YouTrackService.searchIssues` passes the query through to YouTrack's own search (`/api/issues?query=`), so its query language works as in the web UI; a blank query means `for: me #Unresolved sort by: updated desc`. `+` has to be percent-encoded by hand: `URLComponents` leaves it alone and the server reads it as a space
- `YouTrackService.verifyToken` (`GET /api/users/me`) backs Settings' YouTrack "Test Connection". The token is global but the URL is per repository group, so the test runs against every distinct group URL (`SettingsReducer.youTrackInstances`) and names each instance in its verdict. A 200 that is not a YouTrack user throws `.unexpectedResponse` — a wrong base URL usually answers with a web page, not an auth error
- `ClaudeCommand.make(prompt:)` — `claude`, or `claude '<prompt>'` single-quoted for the shell it is typed into, line breaks flattened (a typed newline would submit the line early)
- Terminal.app opens a window at the user's home directory the moment it launches, and a plain `do script` (no target) always makes *another* window — so launching it cold left two windows behind, one at home. `TerminalLauncher.openSystemTerminal` therefore reuses that startup window (`do script … in front window`) when Terminal was not already running, for both the new-window and new-tab behaviors. Terminal's dictionary cannot make a tab (`make new tab` fails with -10000), so a new tab means posting ⌘T — and it must be posted **in-process with `CGEvent`**, not handed to `osascript`. macOS checks the Accessibility grant of whoever posts the event, so an `osascript` child gets checked against `osascript`, which has no grant of its own: it fails with `osascript is not allowed to send keystrokes (-1002)` no matter what the user granted the app, which is why tabs silently came out as windows. `requestNewTerminalTab` gates on `PermissionChecker.isAccessibilityPermitted()` (the app's own grant, what `RepositoryListView`'s Accessibility banner tracks) and posts the event itself
- Because the keystroke is in-process, opening a tab is three steps rather than one script: `prepareScript` activates Terminal and returns the front tab's `tty` (or `""` when it already finished the job), then ⌘T is posted, then `newTabScript` polls until the front window's selected tab is no longer that `tty` and runs the command there. Poll rather than guessing a delay — Terminal reports the new tab asynchronously, and a fixed delay lands the command in the tab that was already there. Both builders are `internal` so the script text is unit-tested. If the keystroke cannot be posted, or the tab never arrives, fall back to a plain `do script`: a window beats opening nothing and beats typing into a tab that may have something running in it
- `TerminalNotificationClient` — `UserNotifications` wrapper for terminal tab notifications (Claude waiting, or a program's OSC 9 / OSC 777). A notification's identifier is its `TerminalSession` id, so a repost for the same tab replaces the old one and a click names the tab to open. The center's delegate is installed on first `post`/`taps` (clicks are only delivered to a delegate); `willPresent` still shows the banner while the app is frontmost, since the waiting tab may be hidden behind another one in the same window

**GitHosting** — PR/MR lookups against github.com and gitlab.com
- `PullRequestClient.fetchDetails` (the row's PR/MR for its branch) and `listOpen` (open PRs/MRs for the create-worktree dialog, `OpenPullRequests.swift`). `listOpen` includes PRs/MRs from forks (GitHub's `isCrossRepository`, GitLab's `sourceProjectId != targetProjectId`) as `isFromFork`, with the fork's owner. Their branch is not on `origin`, so they are checked out from `headRef` — the `refs/pull/<n>/head` / `refs/merge-requests/<iid>/head` that `origin` keeps for every PR/MR. A 200 with a null repository/project throws `.unauthenticated`, as the single fetch does, rather than reading as "no PRs" Each one carries `isAuthoredByViewer` (GitHub's `viewerDidAuthor`; on GitLab, which has no such field, the MR author compared with `currentUser` fetched in the same query), behind the dialog's "Only mine" checkbox (remembered in `worktreeOnlyMyPullRequests`). It filters the listed 50 locally, so an own PR older than the 50 most recently updated does not show

**YouTrackMenu** — YouTrack ticket menu
- `YouTrackButtonReducer` / `YouTrackButtonView` — moves a ticket to a different state
- Offers only the transitions YouTrack reports as reachable (`IssueDetails.stateTransitions`); the row supplies them, this package only applies the chosen one

**TerminalFeature** — embedded terminal panel
- `TerminalSession`, `TerminalViewStore`, `TerminalViewRepresentable`, `TerminalStatusDotView`
- `TerminalPaletteMapping` — `[NSColor]` → `[SwiftTerm.Color]` for `installColors`. The palette crosses the package boundary as `NSColor`, not as a Settings type, so TerminalFeature stays free of a Settings dependency (the same split the fg/bg colors already use); RepositoryFeature resolves the theme and passes the result down. SwiftTerm has no support for reading any theme file format — `Color.parse` handles X11 specs (`#rrggbb`, `rgb:r/g/b`) only, so the plist decoding lives in Settings. `installColors` derives all 256 colors from the 16 plus the terminal's background and foreground, so it must run *after* `nativeForegroundColor`/`nativeBackgroundColor` are set
- Killing a session must go through `TerminalViewStore.killSession` / `killSessions(notIn:)`, which hang up the shell with SIGHUP. Dropping the pane alone does not close the PTY (SwiftTerm leaves a read pending), and SwiftTerm's `terminate()` sends SIGTERM, which interactive zsh ignores. `RepositoryListView` calls `killSessions(notIn:)` whenever the session ids in state change, so reducer-side removals (worktree deletion) hang up too.
- `allowMouseReporting` is driven by the `terminalMouseReporting` setting (default on) and assigned in `TerminalViewRepresentable.updateNSView`, not at creation, so panes pick up a change to the setting. Forcing it off breaks more than clicks: SwiftTerm's `scrollWheel` checks the flag *before* `terminal.mouseMode`, so a TUI on the alternate screen (lazygit, vim) gets the wheel as bare Up/Down arrow keys, which carry no coordinates — scrolling then always moves the focused pane instead of the one under the pointer. Text selection does not need the flag off; ⇧-drag bypasses reporting (`shiftBypassesMouseReporting`)
- `ClaudeAwareTerminalView` re-snaps the cell grid on `viewDidChangeBackingProperties` / `viewDidMoveToWindow` when the window's backing scale differs from the one the grid was measured for, by reassigning `font` (the only public entry to SwiftTerm's `resetFont`). SwiftTerm snaps cell width/height to the pixel grid of the screen current when the font is set and never re-measures on a screen change, so moving the window from an external monitor to the MacBook display (different scale) drew a stale grid: smeared glyphs, cell edges between pixels, wrong column count. Guarded on an actual scale change because the reassignment resizes the PTY (SIGWINCH) and clears the selection
- `ClaudeAwareTerminalView` handles OSC 9 and OSC 777 desktop notifications the way Ghostty does (`TerminalNotification`, `OSC9Payload`), via `registerOscHandler`. SwiftTerm routes OSC 777 to a `notify` delegate method its Mac view never implements, and a registered handler *replaces* SwiftTerm's own for that code — so the OSC 9 handler re-parses ConEmu's `9;4;state;progress` and hands it back to `progressReport(source:report:)`, or Claude Code's progress bar would be lost, and ignores ConEmu's other numbered subcommands (1–12) rather than showing them as a message. A notification calls `ClaudeStatusDetector.attentionRequested()` first, which sets the pane to waiting *silently* (the session learns it with the notification, so the status-change path does not post a second one) and holds it there through idle checks until the user's next keystroke — a build's notification comes with no Claude prompt on screen, and would read as `.active` at the next quiet interval
- `ClaudeStatusDetector` releases a waiting pane on user input, and SwiftTerm's own replies to the child (focus reports, answers to queries) arrive on the same `send(source:data:)` path as keystrokes — as do mouse events, so the call path cannot tell them apart. `TerminalReply` sorts them by shape instead. Claude Code asks for the cell size (`CSI 16 t`) on every focus change, and before that reply (`CSI 6;h;w t`) was recognised, each tab switch released *both* panes it touched; the one left behind settled back at its prompt 1.5 s later, now off screen, and posted "Claude is waiting" again (traced 2026-09-30). The cursor-position report (`CSI r;c R`) is left out on purpose: it is shaped like F3 with a modifier
- `ClaudeStatusDetector` also listens to Claude's own OSC 9;4 progress reports: `9;4;3` when a turn starts, `9;4;0` when it ends (also on exit). Claude Code sends them only to terminals it recognises (Ghostty 1.2+, iTerm2 3.6.6+, ConEmu — checked in 2.1.283), so panes start with `ConEmuANSI=ON` (`TerminalEnvironment`); nothing else in Claude acts on "conemu", whereas claiming Ghostty/iTerm2 would also change its notification channel and keyboard handling. Claude keeps its `❯` input box on screen while it works, so before this a mid-turn pause in output read as waiting and stuck there until a keystroke. While a turn is reported in progress, an idle check ignores the input box and counts only a numbered option (`❯ 1. Yes`) as waiting — permission dialogs come mid-turn and Claude still reports progress while they are up. "Done" reports nothing by itself; the next idle check judges the screen as before (which is also what tells an exit from a finished turn). A non-Claude foreground clears the flag, and a Claude that sends no progress leaves the screen-only judgement unchanged
- The Settings → Terminal "Detect Claude waiting from" picker (`ClaudeStatusDetection` in Settings, mapped by `TerminalPanelView` onto TerminalFeature's own `ClaudeStatusSource`) chooses between that default (`progressAndScreen`), `progressOnly` (Claude in the foreground and not mid-turn *is* waiting, no prompt hunting; the screen is still read mid-turn for dialogs; a Claude that never reports — older, setting off, over ssh, inside tmux — always reads as waiting) and `screenOnly` (the pre-progress behaviour, without `ConEmuANSI`). Fixed per pane at creation, not applied live: the variable can only be set when the shell starts, and switching a pane without it to `progressOnly` would pin it at waiting
- Find (⌘F, ⌘G/⇧⌘G, ⌘E) uses SwiftTerm's own find bar (search field, previous/next, case/regex/whole-word). SwiftTerm opens it only from Edit ▸ Find menu items, which this app does not have, and its show/hide functions are private. So `TerminalFindCommand` sends `performFindPanelAction(_:)` a menu item carrying the tag the real item would (`TerminalViewStore.performFind`). ⌘F belongs to `RepositoryListView`'s always-registered filter shortcut, which decides at press time whether to open the active pane's find bar or focus the list's filter field. It is not handed off to the panel like ⌘T/⌘R, so its registration never changes — on macOS 27 a conditionally inserted shortcut can stop being delivered. ⌘G/⇧⌘G/⌘E sit beside the panel's zoom shortcuts. `ClaudeAwareTerminalView.requestFocus` leaves focus alone when it is already inside the pane: the representable calls it on every update pass, a Claude status change is one, and taking focus unconditionally pulled it out of the find field a moment after ⌘F, so the search text went to the shell
- ⌥←/⌥→ word motion is sent by `ClaudeAwareTerminalView` itself (a local `keyDown` monitor + `OptionArrowWordMotion`), because panes run with `optionAsMetaKey = false` (so Czech Option+4 = `$` works) and in that mode SwiftTerm drops it: legacy input becomes `moveWordLeft:`, which its `doCommand` doesn't handle (bash got nothing), and under the kitty protocol it sends a bare arrow with Option removed (Claude Code moved one character). Sends `ESC b`/`ESC f` normally and `CSI 1;3D`/`CSI 1;3C` when kitty flags are active. A monitor because SwiftTerm's `keyDown` is `public`, not `open`
- The global `terminalStartupCommand` setting (Settings → Terminal), or a repository group's own `RepoGroupSettings.terminalStartupCommand` when that is non-blank (a blank group command means "use the global one", not "none" — for "none", the group sets `skipGlobalTerminalStartupCommand`), rides on `TerminalSession.startupCommand` (trimmed, `nil` when blank) into the first built-in tab a repository opens. Tabs opened with + / ⌘T get it only when `terminalStartupCommandInNewTabs` is on (off by default — extra tabs are usually wanted as a plain shell); a retried tab gets it only if the tab it replaces had one. `ClaudeAwareTerminalView` types it (plus `\r`) on the shell's **first output**, not right after `startProcess`: bytes written before the line editor is up are echoed by the tty as typeahead and then again at the prompt, so the command showed twice. It is typed, not passed as `zsh -c`, so it runs in the user's interactive shell, lands in history, and the shell stays open after it. External terminals (Terminal.app, iTerm, Warp) do not get it
- The font arrives already resolved (an `NSFont`, not a name and a size) and is assigned in the same place, but **only when the font name or point size actually differs** — compared field by field rather than with `!=`, which also weighs matrix and descriptor attributes the view may have derived — unlike the flags beside it. SwiftTerm's `font` setter rebuilds the bold/italic faces, calls `selectNone()`, and re-derives cols/rows from the new cell size in `resetFont()` — which resizes the PTY and SIGWINCHes the shell. That is correct for a deliberate zoom and wrong on every unrelated update pass, which is why the assignment is guarded

**GitGraphFeature** — commit graph
- `GitGraphReducer` / `GitGraphView` — the commit table (`GitGraphLayout` assigns lanes, `GitGraphColumnWidths` persists column widths)
- `CommitDetailReducer` / `CommitDetailView` — the bottom pane: the selected commit's changed files on the left, the selected file's diff on the right, in a read-only `DiffViewer`
- The commit table is a `List(selection:)` (not a `ScrollView` + `LazyVStack`), so selection and ↑/↓ keyboard navigation are native; the list takes focus on open. Rows need `.listRowInsets(EdgeInsets())`, `.listRowSeparator(.hidden)` and `defaultMinListRowHeight = GitGraphRowView.rowHeight` to stay flush — any inter-row gap breaks the vertical lane lines. The "Load More" row is `.selectionDisabled()` so arrow keys skip it, and the column header stays a `Section` header *inside* the list so it keeps the rows' insets
- Use one list-level `.contextMenu(forSelectionType:)`, never per-row `.contextMenu` — ⌘A would make AppKit build every row's menu (the same O(rows²) freeze documented in `FileChangeListView`)
- The selection binding ignores nil writes: the list emits one when it cannot carry selection across a wholesale row replacement, and a background refresh must not close the diff pane
- `selectedCommitHash` is kept on the parent state alongside `commitDetail` on purpose, so a row observes only that one property instead of re-rendering whenever the child loads a file list or diff
- `commitTapped` builds the child state and sends `.commitDetail(.task)` itself rather than relying on the view's `.task`, so re-selecting always reloads even when SwiftUI reuses the pane
- Selection is read-only: it shells out to `git show` only, and never checks anything out
- The commit menu is the graph's one write path (`GitGraphCommitActions.swift`, grouped under `Action.commitAction`): check out a branch on the commit, a remote branch's local namesake, or the commit itself (detached); new branch / new worktree from the commit (a name sheet, `BranchForm`); cherry-pick onto the current branch; revert. Detached checkout, cherry-pick and revert are confirmed in an alert naming the current branch; a branch checkout is not. Only one runs at a time (`runningCommitAction`, shown in the header; the menu is disabled meanwhile). A stop on conflicts offers Abort or Resolve Later. Each success reloads the graph and sends `delegate(.repositoryChanged)` or `delegate(.worktreeCreated)`; `RepositoryRowReducer` and `RepositoryListReducer` (for the terminal panel's graph) turn those into a row refresh or a group rescan. Worktree base path and copy paths come from the presenter via `GitGraphReducer.State.forRepository(path:name:)` (RepositoryFeature), so GitGraphFeature needs no Settings dependency
- Search (⌘F; the header's field with a Message / Author / Hash / File Path / Changes picker) narrows the graph through git, not over the loaded rows: `GitLogHelper.loadCommits(…search:)` adds `--grep` / `--author` (both `-i --fixed-strings`, since typed text like `fix(` is not a regex), `-i -S` or pathspecs to the same `git log`; Hash resolves through `git rev-parse --verify <q>^{commit}` and shows that one commit. It runs as you type, debounced (`GitGraphReducer.searchDebounce`) and `cancelInFlight` — `ProcessRunner` kills the superseded git, which matters for a slow `-S`. Clearing reloads at once. A changed search resets `commitLimit` to one page; Load More pages through the search
- Only a pathspec gets its parents rewritten by git (`--parents` → nearest matching ancestor, so a file's history is still a connected graph). `--grep`/`--author`/`-S` hide commits but leave parents pointing at them, so the layout would keep a lane open for each down to the bottom. For those, `GitLogCommit.graphParents` (what `GitGraphLayout` follows) keeps only parents that are themselves listed, while `parents` stays real so `isMerge` still holds
- A path query becomes three pathspecs (`:(icase)q`, `:(glob,icase)**/*q*`, `:(glob,icase)**/*q*/**`): a glob only matches whole paths, so without the `/**` one a directory name matched nothing
- Escape clears a non-empty search while the field has focus and closes the sheet otherwise, so the cancel shortcut sits on a hidden button rather than on Close (clicking Close leaves focus in the field, so Close itself cannot decide by focus). Return/↓ in the field move focus to the commit list. After a search changes, the list scrolls once its results load: to the selected commit if still listed, else the first result, or HEAD when cleared
- Keyboard focus between the commit list and the file list is an explicit `@FocusState` (`GitGraphPane`), not left to clicks: with a plain `Bool` the commit list kept focus after a file was clicked, so ↑/↓ kept walking the commits. Clicking a row moves focus to its list via a `.simultaneousGesture(TapGesture())` on the row, not via the file selection binding — the list also writes its selection back on reload (moving focus on those writes stole it from the commit list after every ↑/↓), and a click on the already-selected first file changes no selection at all; selecting a commit (click or key) moves it back to the commit list — the file list is swapped for a spinner while the new commit loads, so leaving focus there left ↑/↓ reaching nothing; → (commit list, with the pane open) and ← (file list) switch between them

**RepositoryFeature** — top-level feature UI and reducers
- `RepositoryListReducer` / `RepositoryListView` — main list state
- `RepositoryRowReducer` / `RepositoryRowView` — per-row state and actions
- `RepoGroupReducer` / `RepoGroupView` — grouped repo display
- Live refresh: after every scan (`scanCompleted`, `addRepositorySucceeded`, group removal) `watchRepositories` points `GitRepositoryWatcherClient` at all rows, restarting the watch only when the set of row paths changed. `repositoriesChangedOnDisk` sends the row `changedOnDisk(kinds)`, or rescans the group for `.worktreeList` (a worktree added or removed in a terminal). `changedOnDisk` re-reads git status (`didFetchStatusAfterChangeOnDisk`) and/or the stash, but unlike `refresh` asks YouTrack and the PR provider only when the branch changed, and the PR provider alone when the upstream moved (remote branch appeared/vanished, behind count changed, unpushed count dropped) — it can fire on every saved file, and a local commit asks nothing. Both status actions share `applyStatus`. A row's status fetches (`onAppear`, `refresh`, `changedOnDisk`) share one cancel id with `cancelInFlight`: during a checkout or pull, changes arrive every 0.3 s and an older, slower `git status` landing last would leave a mid-checkout snapshot on the row. A change that cancels a refresh's fetch reports as a refresh (`isRefreshingStatus`), so the refresh's YouTrack/PR lookups are not lost. A `.stash` arriving with `.status` is checked after the status lands (`isStashCheckPending`), once, because the stash menu is keyed on the branch that read may change. A `.stash` arriving alone for the terminal panel's repository also refreshes the toolbar's git menu copy, which otherwise re-checks its stash only when a status read syncs it (`syncTerminalGitMenu`). The periodic refresh stays as a fallback for what is not on disk (PR, pipeline and ticket state)
- `CreateWorktreeButton` creates from one of three sources (`WorktreeSource`): a typed branch, a YouTrack ticket (searched with `YouTrackClient.searchIssues`, debounced 300 ms; picking one fills the branch name from `BranchNameFormatter.branchName`, still editable, and always makes a new branch off the chosen base), or an open PR/MR (checked out on its own branch with `createNewBranch: false` — a new branch off it would leave the worktree's commits outside the PR; a fork's PR/MR goes through `GitWorktreeCreator.createWorktree(fetching:branchCandidates:…)` instead). The ticket source is offered only when the group has a YouTrack URL. The dialog opens on the tab the repository group picks in Settings → Repository Groups (`RepoGroupSettings.defaultWorktreeSource`, `openingWorktreeSource(fallback:)`; `WorktreeSource` lives in Settings for that reason), falling back to Branch where Ticket is not offered; switching tabs lasts for that opening only. A group that has not picked one uses the app-wide `defaultWorktreeSource` key, the setting this replaced — no longer written or shown, kept so an existing choice carries over. The "After creating" choice (`WorktreeCreationFollowUp`, remembered in `worktreeCreationFollowUp`) becomes a `WorktreeTerminalLaunch` riding on the row's `worktreeCreated(path:launch:)`. The new worktree has no row until a scan finds it, so the list parks the launch in `pendingWorktreeLaunches` (keyed by symlink-resolved path: the creator builds the path, git reports its realpath) and opens the built-in terminal from whichever `didScanGroup` brings the row in. "Run Claude" replaces the group's startup command in that first tab with `ClaudeCommand.make(prompt:)`, the prompt prefilled from the ticket or PR
- `RepositoryRowView` gives the title area the lowest `layoutPriority` with a minimum width (260 pt × UI scale), so the stack sets that aside first; the menus and icon buttons sit in `RowActionsLayout`, which uses one line when it fits and otherwise splits into two balanced lines. That way a narrow window wraps the actions before the title truncates. It is a `Layout`, not `ViewThatFits`, so the menus' alerts and dialogs are not duplicated. The action bar carries a hidden, zero-wide `ToolButton` at the configured size (`toolButtonHeightStrut`) whenever any tool button is placed in the row, so a row without one (no Android/Xcode project) is as tall as its neighbours and every row grows when the size goes to Large
- Which action bar items a row shows, their order and the tool buttons' size come from `RepositoryRowLayout` (Settings ▸ Repository Rows, `repositoryRowLayout` key, a JSON string in user defaults), read by the row with `@SharedReader`. Items (`RepositoryRowItem`) reorder only within their zone: menus & icons vs. the tool buttons (Android Studio, Xcode, Claude Code); the worktree create/delete and group remove buttons are fixed at the end. Decoding drops unknown items and appends ones a newer version added, so adding a case needs no migration. The type spells out `==`: as a `RawRepresentable` it would otherwise compare JSON strings. The size reaches `ToolButton` through AppUI's `toolButtonSize` environment value (`ToolButtonSize`; `.small` is icon-only)
- Each item is placed (`RepositoryRowItemPlacement`) in the row, in the "⋯" menu, or hidden (`hidden` / `inMoreMenu`, disjoint). Every item defaults to the row. The "⋯" menu (`RepositoryRowMoreMenu.swift`) is not an item: it is drawn at the end of the menus and icons only while an item is placed in it (`showsMoreMenu`), and lists those items in order, menus and icons first. In it the menus become submenus (`GitActionsSubmenu`, `YouTrackSubmenu`, `TuistSubmenu`, a disabled entry naming the running operation while one runs) and the buttons plain entries (`AndroidStudioMenuItem`, `XcodeProjectMenuItem`, `ClaudeCodeMenuItem`, the PR/pipeline/approval titles taken from their buttons' tooltips). A menu entry cannot present an alert or dialog, so each of those views' presenters is split out into a modifier (`gitActionsMenuPresentations`, `youTrackMenuPresentations`, `tuistPresentations`, `androidStudioPresentations`, `xcodeProjectPresentations`, `claudeCodePresentations`) that the in-row view applies to itself and the row applies on its action bar's background for the items placed in the menu only — a second presenter of the same state would fight the first
- Per-button Reducer+View pairs: `CreateWorktreeButton`, `DeleteWorktreeButton`, `TerminalButton`, `ClaudeCodeButton`, `XcodeProjectButton`, `TuistButton`, `TicketButton`, `ShareButton`, `WebButton`
- `TerminalLayoutReducer` / `TerminalLayoutView` / `TerminalPanelView`
- Two drag-to-reorder helpers, both `onDrag`/`onDrop` with a `public.text` payload for reasons documented in `ReorderableDrag.swift` (a `Section` header cannot be a `draggable` source, an undeclared UTType never matches a drop). `View.reorderable(payload:isEnabled:isTargeted:insertionEdge:onDrop:)` moves on release and draws an insertion line; the sidebar's repository group headers use it because sections under a `List` cannot slide. `View.liveReorderable(id:isEnabled:draggedId:onMove:)` (`LiveReorderableDrag.swift`) moves the dragged item on `dropEntered`, so the row animates around the pointer during the drag like browser tabs; the terminal tab pills use it. The dragged id lives in a `@State` shared by the row because a drop delegate cannot read the pasteboard synchronously. Reducers treat what arrives as untrusted: `repositoryGroupDropped` ignores a path that names no group, `terminalLayout(.moveTab)` ignores a session id that names no tab or a tab of another repository. Both apply the same rule, the dragged item takes the target's place, and `moveTab` applies it inside `withAnimation`
- Terminal notifications arrive two ways. `terminalSessionStatusChanged` entering `.waitingForInput` posts a generic "Claude is waiting" one; `terminalNotificationReceived` (a program's OSC 9 / OSC 777) sets the session to `.waitingForInput` itself and posts the program's own title and body, with the tab as subtitle. Both skip posting when the `terminalNotifications` setting is off, or the tab is the panel's active one *and* the app is frontmost; leaving `.waitingForInput` withdraws the notification. A tab opened with a startup command posts nothing for its *first* `.waitingForInput` (`TerminalSession.awaitsStartupPrompt`): with `claude` as the startup command, that prompt is Claude having booted, and users open the next repository's terminal before it does. `onAppear` subscribes to clicks; `terminalNotificationTapped` opens the panel on that exact session (`openTerminal` then `activate`) and brings the app forward
- The terminal overlay takes **scoped stores**, never row values: `TerminalLayoutView.repositoryGroups` is `[StoreOf<RepoGroupReducer>]` and `activeRowStore` is resolved in `RepositoryListView`. TCA's `IdentifiedArray` observation compares element ids only, so a row handed over as a value freezes its counts at whenever the overlay last rebuilt — that was the stale push status in terminal view (2026-09-07). Store collections are wrapped in `Array(...)` because the sidebar is a `LazyVStack`
- Terminal tabs survive a relaunch (`TerminalTabArchive.swift`). `RepositoryListView` sends `saveTerminalTabsRequested` on `onDisappear` *and* on `NSApplication.willTerminateNotification` — quitting with the window open never takes it off screen, and closing the window releases the panes (hanging up their shells) before any quit. Each tab is saved with its shell's *current* directory (`TerminalViewStore.currentDirectories()`, read from the kernel with `proc_pidinfo(PROC_PIDVNODEPATHINFO)` on the shell pid — not OSC 7, which zsh only emits inside Terminal.app), the startup command it ran (stored verbatim: restore happens before the scan has placed the repo in a group, so settings can't be resolved yet), and which tab was on screen / remembered per repo. Failed tabs are not saved. A tab with Claude Code in its foreground is also saved with its conversation id (`TerminalPaneSnapshot.claudeSessionId`) and reopens typing `claude --resume <id>` instead of its startup command (`TerminalSession.commandToType`; `startupCommand` keeps the configured one for retries and the next save). The id comes from Claude Code's own per-process record, `<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<pid>.json` (`ClaudeSession`) — undocumented, so any surprise in it reads as "no session". Every process of the pty's foreground group is checked, but only one whose argv is Claude's (a stale record must not be pinned on a reused pid), and only a UUID is accepted, since it is typed into a shell. The file is written synchronously by `TerminalTabArchiveClient`, not `@Shared(.fileStorage)`, whose writes within a second of the last one wait on a timer that never fires at quit. `restoreTerminalTabs` (sent once from `onAppear`) drops tabs whose repository directory is gone and reopens ones whose own directory is gone at the repo root; the panel reopens only if it was open, otherwise the shells start when it is next shown. `didScanGroup` fills in the toolbar's button copies once the restored repo's row appears
- The toolbar's Xcode, Tuist and YouTrack buttons scope the opened row's own stores (`activeRowStore.scope(\.xcodeButton/\.tuistButton/\.youtrackButton, …)`), not copies in `TerminalLayoutReducer.State`. For YouTrack a copy would also go stale: after a transition the row refetches the ticket, and only that fetch knows the transitions now reachable. Hiding the panel sets `terminalLayout = nil`, and `ifLet` cancels that child's effects, so a generate running in a copy got its tuist process SIGTERMed with no error shown, and the row never knew it had run. Because the list stays mounted at opacity 0 under the overlay, both views then bind the same alert state; `presentsButtonAlerts` (environment in AppUI, so the YouTrackMenu package can read it; turned off on the hidden list) leaves the visible one as the only presenter. The Android Studio, web, ticket and git menu buttons are still copies, synced by `syncTerminalButtons`

## Architecture

**TCA Pattern:**
- Reducers handle state + side effects
- States are immutable
- Actions trigger changes
- Effects wrap async work

**Core Model (ScannedRepository) — in GitCore:**
- path, name, directory
- isWorktree, branchName, isMergeInProgress
- unstagedChangesCount, stagedChangesCount, unpushedCount, behindCount, hasRemoteBranch

**Git status is fetched in one call:**
- `GitStatusDetector.getBranchAndChanges` runs `git status --porcelain=v2 --branch` and parses everything (branch, staged/unstaged counts, unpushed, behind, remote branch)
- `RepositoryRowReducer.fetchAll` fires 1 git process per row
- Exception: git reports ahead/behind only against an upstream, so for a branch without one `getStatus` follows up with `rev-list --count HEAD --not --remotes` (commits on no remote-tracking branch) for `unpushedCount`. It stays 0 when the repository has no remote-tracking refs at all, since every commit would count

**Services (protocol-based, DI via `@Dependency`):**
- `GitClient` (git ops, defined in GitCore)
- `XcodeService`, `YouTrackService`, `LastOpenedDirectoryService` (in ToolsIntegration)

## Build & Run

**Build:**
- `open BridgeCommander.xcodeproj` (the project references all local SPM packages under `Packages/`)
- Or: `xcodebuild -project BridgeCommander.xcodeproj -scheme BridgeCommander -destination 'platform=macOS' build`

**Run:**
- ⌘R in Xcode
- Or: `open -a BridgeCommander`

**Test:**
- Unit tests live in per-package `Tests/` targets and use Swift Testing (`import Testing`, `@Test`/`#expect`).
- Run a single package's tests: `swift test --package-path Packages/<Name>` (e.g. `swift test --package-path Packages/GitCore`).
- Warnings are errors: the app target sets `SWIFT_TREAT_WARNINGS_AS_ERRORS`, and every `Package.swift` ends with a loop adding `.treatAllWarnings(as: .error)` to all its targets, tests included (a new package needs the same loop). Test targets are compiled only by `swift test`, not by the app build, so run them after touching tests or bumping a dependency that deprecates something.
- In `TestStore` assertions, mutate `@Shared` state as `$0.$x.withLock { $0 = … }`; the plain setter is deprecated.
- When adding tests to a package that has none, add a `.testTarget(name: "<Name>Tests", dependencies: ["<Name>"])` to that package's `Package.swift`.
- Prefer pure, dependency-free logic (helpers, models) for unit tests; code that shells out to git is verified by build + manual run.
