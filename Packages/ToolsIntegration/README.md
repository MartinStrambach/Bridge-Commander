# ToolsIntegration

Xcode, YouTrack, Android Studio, Terminal, Claude Code.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- `@DependencyClient`s: `XcodeClient` (`XcodeService.swift`), `YouTrackClient` (`YouTrackServiceImpl.swift`, over the static `YouTrackService` namespace), `LastOpenedDirectoryClient` (`LastOpenedDirectoryService.swift`), `DerivedDataUsageClient`
- `YouTrackIssueModels.swift` — `IssueDetails`, `TicketState`, `TicketStateTransition`, `CodeReviewState`
- `TerminalLauncher` (`TerminalApp`: Terminal.app, iTerm2, Ghostty, Warp; also starts Claude Code, with `command: "claude"`), `AndroidStudioLauncher` / `AndroidStudioDetector`
- `XcodeProjectDetector`, `XcodeProjectGenerator`, `XcodeDerivedDataHelper`
- `DerivedDataUsageScanner` (Settings ▸ Branches & Worktrees ▸ Xcode DerivedData) sorts DerivedData's folders into `DerivedDataUsage.Kind`s: a folder whose `info.plist` names a `WorkspacePath` is `inUse` or `orphaned` by whether that path still exists; one without is a `leftover` when its name has Xcode's project shape (`<name>-` plus 28 lowercase letters, which Xcode derives from the MD5 of the workspace path; checked against all 90 folders with a plist, 2026-10-15), else a `sharedCache` (`ModuleCache.noindex`, `CompilationCache.noindex`, …). Leftovers hold only `Logs`/`SourcePackages`: the matcher in `XcodeDerivedDataHelper` reads the plist, so it can never delete them. Sizes are counted as `du` counts them (allocated blocks, hard links once, symbolic links not followed, other volumes not entered) with `getattrlistbulk`, which returns a whole batch of directory entries' attributes per call, eight folders at a time, deletable kinds first: 7 s on 168 GB / 2.2 million items, where `fts` + `lstat` four at a time took 10 s and `du -sk` 40 s, same total (2026-10-15). The work is in the kernel, so more workers gain nothing. The walk enters a directory's subdirectories only after reading it, so open descriptors stay at the tree's depth (a GUI app's soft limit is 256). In a `getattrlistbulk` entry the common attributes are always packed, but a directory's carries only the directory group and anything else's only the file group, even with `FSOPT_PACK_INVAL_ATTRS`. A measurement streams a `DerivedDataUsage` after each folder, so the page fills in as it goes, and keeps each folder's kind and size in `folders` so a deletion can be subtracted. `deleteFolders(of:)` removes the folders of a kind in `deletableKinds` (`orphaned`, `leftover`) and classifies them afresh first, so it never trusts a measurement taken before a worktree reappeared at the same path. Removal is the slow part, one item after another (about 6 s per 7 GB project folder), so it first empties the folders' subfolders eight items at a time (two such folders: 5 s instead of 12.7 s), then removes each folder through `XcodeDerivedDataHelper.removeFolder`, whose Trash fallback handles whatever the first pass left
- `TuistCommandHelper`, `BranchNameFormatter`, `FileOpener`, `PermissionChecker`
- `FileOpener.openFileInIDE` takes a repository-relative path (the staging panel) or an absolute one with an optional line (a file ⌘-clicked in a terminal, which may lie outside the repository). Only Xcode gets the line (`xed --line`); Android Studio and other apps are reached through `open`, which cannot pass one
- `BranchNameFormatter` goes both ways: `format` turns a branch into the row's display text, `branchName(ticketId:summary:template:)` names a branch after a YouTrack ticket. The template (`ticketBranchNameTemplate`, `{ticket}`/`{summary}` placeholders) defaults to `{summary}_{ticket}`, the shape `format` reads back as the bare summary; the summary becomes a lowercase ASCII slug with diacritics folded (Czech summaries stay readable), cut at a word boundary at 50 characters
- `YouTrackService.searchIssues` passes the query through to YouTrack's own search (`/api/issues?query=`), so its query language works as in the web UI; a blank query means `for: me #Unresolved sort by: updated desc`. `+` has to be percent-encoded by hand: `URLComponents` leaves it alone and the server reads it as a space
- `YouTrackService.verifyToken` (`GET /api/users/me`) backs Settings' YouTrack "Test Connection". The token is global but the URL is per repository group, so the test runs against every distinct group URL (`SettingsReducer.youTrackInstances`) and names each instance in its verdict. A 200 that is not a YouTrack user throws `.unexpectedResponse` — a wrong base URL usually answers with a web page, not an auth error
- `YouTrackIssueCreation.swift` backs the create-worktree dialog's New Ticket tab: `listProjects` (`GET /api/admin/projects`, which also answers for non-admins with the projects they can read; archived ones dropped), `projectFields` (`GET /api/admin/projects/{id}/customFields`), `createIssue` (`POST /api/issues`) and `applyFieldValues`. The create takes the project's database id (`0-1`), not its short name. Nothing is tied to a project: every field whose bundle is an enum, owned (subsystem), version or build bundle is offered as a `YouTrackChoiceField`, in the project's order, with its defaults, `canBeEmpty` and `isMultiValue`. State is left to the In Progress transition and user fields to Assign to me (matched by YouTrack's default name, Assignee, whose accepted users come from its bundle's `aggregatedUsers`). The project-level field type does not show that a state-machine workflow drives a field (per-platform review fields can read as plain enums), and such a field ignores value writes and only moves through events named for the action ("needed"), not the value they lead to (Waiting). So `projectFields` also reads the project's 50 newest tickets, and for each field one of them still has at its starting value, offers that value followed by the events YouTrack lists from it (`applyingWorkflowEvents`, `eventDriven`). Without such a ticket the field keeps its values, and a pick no event matches comes back as a warning. Only the assignee goes into the create. The picked fields are set afterwards by `applyFieldValues`: it reads the filed ticket's fields and plans each (`fieldUpdates`) as an event for a `StateMachineIssueCustomField` (matched on its `presentation`, case-insensitively), a write to `customFields/{id}` with the issue field's own `$type` for anything else, or skips it when the ticket already has the value. Each field is set on its own, so one refusal does not cost the others. Projects can make a field conditional (shown only while another field holds certain values: Detected in for Type Bug, the per-platform CR fields from State In Progress on), and YouTrack leaves a hidden field out of the ticket's `customFields` entirely, so it cannot be set and `fieldUpdates` plans it as `.hidden`. `projectFields` reads each field's `condition` (`YouTrackFieldCondition`), every field's defaults (`initialValues`) and the State field's name, and `YouTrackProjectFields.shows` evaluates a condition against picks, so the form offers only fields the ticket will show. `applyFieldValues` retries hidden fields while the rest of its batch changed something, since a pick in the same batch (Type) may be what shows them. Checked against a live YouTrack instance on 2026-10-22
- `ClaudeCommand.make(prompt:)` — `claude`, or `claude '<prompt>'` single-quoted for the shell it is typed into, line breaks flattened (a typed newline would submit the line early)
- Terminal.app opens a window at the user's home directory the moment it launches, and a plain `do script` (no target) always makes *another* window — so launching it cold left two windows behind, one at home. `TerminalLauncher.openSystemTerminal` therefore reuses that startup window (`do script … in front window`) when Terminal was not already running, for both the new-window and new-tab behaviors. Terminal's dictionary cannot make a tab (`make new tab` fails with -10000), so a new tab means posting ⌘T — and it must be posted **in-process with `CGEvent`**, not handed to `osascript`. macOS checks the Accessibility grant of whoever posts the event, so an `osascript` child gets checked against `osascript`, which has no grant of its own: it fails with `osascript is not allowed to send keystrokes (-1002)` no matter what the user granted the app, which is why tabs silently came out as windows. `requestNewTerminalTab` gates on `PermissionChecker.isAccessibilityPermitted()` (the app's own grant, what `RepositoryListView`'s Accessibility banner tracks) and posts the event itself
- Because the keystroke is in-process, opening a tab is three steps rather than one script: `prepareScript` activates Terminal and returns the front tab's `tty` (or `""` when it already finished the job), then ⌘T is posted, then `newTabScript` polls until the front window's selected tab is no longer that `tty` and runs the command there. Poll rather than guessing a delay — Terminal reports the new tab asynchronously, and a fixed delay lands the command in the tab that was already there. Both builders are `internal` so the script text is unit-tested. If the keystroke cannot be posted, or the tab never arrives, fall back to a plain `do script`: a window beats opening nothing and beats typing into a tab that may have something running in it
- `TerminalNotificationClient` — `UserNotifications` wrapper for terminal tab notifications (Claude waiting, or a program's OSC 9 / OSC 777). A notification's identifier is its `TerminalSession` id, so a repost for the same tab replaces the old one and a click names the tab to open. The center's delegate is installed on first `post`/`taps` (clicks are only delivered to a delegate); `willPresent` still shows the banner while the app is frontmost, since the waiting tab may be hidden behind another one in the same window
