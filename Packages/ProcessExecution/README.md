# ProcessExecution

`ProcessRunner` shells out to external processes (`runGit(arguments:at:)` for git) and collects stdout/stderr through pipes read by `readabilityHandler`s, so a chatty process never fills a pipe buffer and blocks.

## Gotchas

- **The result waits for both pipes' end of file, not just the exit** (`ProcessCompletion`). Built in the termination handler, it raced a readability handler that had already taken the last chunk with `availableData` but not appended it: setting the handler to nil does not wait for a call under way, so the final read to the end found the pipe empty. Under load about one `git status` in a thousand exited 0 with no output — the row lost its changes and showed "No remote" until the next read — and multi-chunk output (`git log --stat`) lost a chunk from the middle. A handle's handler calls are serial, so the empty read marking end of file comes after every append. The exit also no longer blocks in that final read while a child the process left running holds a pipe: the result goes `pipeDrainTimeout` (2 s) after the exit, without what that child writes later, and the command is recorded in the activity log as an error — Go's os/exec does the same with WaitDelay and ErrWaitDelay. Known culprits are an ssh ControlPersist master and an old `git-credential-cache--daemon`, both of which inherit git's stderr. The read end is closed at end of file, and the timeout captures only the completion: holding the pipes for it kept hundreds of descriptors open during a burst. `ProcessCompletionTests` pins the ordering; the race itself only showed in a stress run (6000 concurrent `git status`: 7 empty before, 0 after)
- **Every exit path must release the pipes.** A launch that fails (`process.run()` throws, e.g. because the working directory of a just-deleted worktree is gone) never reaches the termination handler, and the never-launched `Process` plus the readability handlers keep both pipes open: six descriptors per failure. A GUI app gets launchd's soft limit of 256 descriptors, so a few dozen failures exhausted it. From then on `Pipe()` does not fail; it silently returns handles on fd 0, and every launch, in every repository, fails with "Failed to start process: … Bad file descriptor" until the app is restarted. The `catch` path therefore clears the termination and readability handlers and closes all four pipe ends. `ProcessRunnerTests.failedLaunchesDoNotLeakFileDescriptors` guards it.
- To inspect a running app's descriptors: `lsof -p $(pgrep -x BridgeCommander) | wc -l`.
- **The resolved git binary can vanish under the running app.** `runGit` launches the binary `xcrun --find git` names (inside the selected Xcode) rather than the `/usr/bin/git` shim, to save the shim's ~5 ms per call. An Xcode update deletes or renames that Xcode (Xcodes.app replaces one release candidate with the next); with the path cached for the app's lifetime, every git call then failed to launch — rows stopped updating, ⌘R did nothing, a deleted worktree's row stayed (its removal goes through `/bin/sh`, so the folder did go) — until a restart. `ResolvedExecutable` checks the file is still there before each use and resolves again once it is not.
- **Cancellation terminates only what reads.** `run` takes a `ProcessCancellation`: `.terminate` (the default) does not launch the process in a task already cancelled and SIGTERMs it when the task is cancelled while it runs; `.finish` launches it and lets it run to the end regardless. `runGit` picks `.terminate` for read-only commands (`GitCommandLog.isReadOnly`) and `.finish` for the rest, as do GitCore's worktree scripts: a `stash -u`, pull or merge terminated half-way can leave the repository half done, and an `--abort` run as cleanup after a cancellation has to happen. The already-cancelled check is needed because `withTaskCancellationHandler` calls `onCancel` at once in such a task, before the launch, when there is nothing to terminate: every superseded refresh's follow-up commands then ran to the end. A cancellation landing between that check and the launch is caught after `process.run()` (`ProcessCompletion.processLaunched`). The result says `wasCancelled` only when the process was not launched or died of the signal the cancellation sent — one that exited by itself first keeps its real result. The flip side: in a cancelled task a read-only probe returns a failure, not an answer, so a multi-step operation that decides what to change from a probe after a cancellation must not run in the cancelled task (`GitCommitActionHelper.apply` runs in its own unstructured task)
- **`runGit` records into the activity log** (`GitCommandLog`): commands that change something always, read-only ones only when they fail or when Settings asks for all of them. `run` records nothing — it also runs osascript, xcodebuild and simctl — so a git command launched another way (a `/bin/sh` script) has to record itself, as GitCore's worktree helpers do
