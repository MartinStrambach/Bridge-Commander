# RepositoryFeature

Repository list/row views and reducers (top-level feature).

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- `RepositoryListReducer` / `RepositoryListView` — main list state
- `RootRepositoryView` hosts the window's sections — Repositories and the Homer console (`HomerFeature`, from the Homer-console-mac-app repository) — switched by AppUI's `AppSectionSwitcher`, which stands where the window title used to at the start of each section's header; the choice is remembered in `selectedAppSection`. The list stays mounted (opacity 0) under the console, like it does under the terminal overlay, so switching back costs nothing and terminals keep running; it is `.disabled` meanwhile so its ⌘R/⌘T/⌘F/⌘A do not fire from under the console. The switcher is only reachable with the terminal panel closed (the overlay covers the list's header), and the panel opening any other way (a notification click, tabs restored at launch) switches back to Repositories, so the console never sits over a terminal holding keyboard focus. The Homer store is created here too and sent `start` from the root `.task`, not from the console's own view, because the switcher's open-question badge (summed over every Homer instance) needs the sessions from launch. The console takes the switcher as its header's leading view, and the app's text scale through `homerUIFontScale` — it has its own copy of AppUI's scaling helpers (at `package` access, so the names do not clash here) and does not read `uiFontScale`
- `RepositoryRowReducer` / `RepositoryRowView` — per-row state and actions
- `RepoGroupReducer` / `RepoGroupView` — grouped repo display
- Live refresh: after every scan (`scanCompleted`, `addRepositorySucceeded`, group removal) `watchRepositories` points `GitRepositoryWatcherClient` at all rows, restarting the watch only when the set of row paths changed. `repositoriesChangedOnDisk` sends the row `changedOnDisk(kinds)`, or rescans the group for `.worktreeList` (a worktree added or removed in a terminal). `changedOnDisk` re-reads git status (`didFetchStatusAfterChangeOnDisk`) and/or the stash, but unlike `refresh` asks YouTrack and the PR provider only when the branch changed, and the PR provider alone when the upstream moved (remote branch appeared/vanished, behind count changed, unpushed count dropped) — it can fire on every saved file, and a local commit asks nothing. Both status actions share `applyStatus`. A row's status fetches (`onAppear`, `refresh`, `changedOnDisk`) share one cancel id with `cancelInFlight`: during a checkout or pull, changes arrive every 0.3 s and an older, slower `git status` landing last would leave a mid-checkout snapshot on the row. A change that cancels a refresh's fetch reports as a refresh (`isRefreshingStatus`), so the refresh's YouTrack/PR lookups are not lost. A `.stash` arriving with `.status` is checked after the status lands (`isStashCheckPending`), once, because the stash menu is keyed on the branch that read may change. A `.stash` arriving alone for the terminal panel's repository also refreshes the toolbar's git menu copy, which otherwise re-checks its stash only when a status read syncs it (`syncTerminalGitMenu`). The periodic refresh stays as a fallback for what is not on disk (PR, pipeline and ticket state)
- `CreateWorktreeButton` creates from one of three sources (`WorktreeSource`): a typed branch, a YouTrack ticket (searched with `YouTrackClient.searchIssues`, debounced 300 ms; picking one fills the branch name from `BranchNameFormatter.branchName`, still editable, and always makes a new branch off the chosen base), or an open PR/MR (checked out on its own branch with `createNewBranch: false` — a new branch off it would leave the worktree's commits outside the PR; a fork's PR/MR goes through `GitWorktreeCreator.createWorktree(fetching:branchCandidates:…)` instead). The ticket source is offered only when the group has a YouTrack URL. The dialog opens on the tab the repository group picks in Settings → Repository Groups (`RepoGroupSettings.defaultWorktreeSource`, `openingWorktreeSource(fallback:)`; `WorktreeSource` lives in Settings for that reason), falling back to Branch where Ticket is not offered; switching tabs lasts for that opening only. A group that has not picked one uses the app-wide `defaultWorktreeSource` key, the setting this replaced — no longer written or shown, kept so an existing choice carries over. The "After creating" choice (`WorktreeCreationFollowUp`, remembered in `worktreeCreationFollowUp`) becomes a `WorktreeTerminalLaunch` riding on the row's `worktreeCreated(path:launch:)`. The new worktree has no row until a scan finds it, so the list parks the launch in `pendingWorktreeLaunches` (keyed by symlink-resolved path: the creator builds the path, git reports its realpath) and opens the built-in terminal from whichever `didScanGroup` brings the row in. "Run Claude" replaces the group's startup command in that first tab with `ClaudeCommand.make(prompt:)`, the prompt prefilled from the ticket or PR
- `RepositoryRowView` gives the title area the lowest `layoutPriority` with a minimum width (260 pt × UI scale), so the stack sets that aside first; the menus and icon buttons sit in `RowActionsLayout`, which uses one line when it fits and otherwise splits into two balanced lines. That way a narrow window wraps the actions before the title truncates. It is a `Layout`, not `ViewThatFits`, so the menus' alerts and dialogs are not duplicated. The action bar carries a hidden, zero-wide `ToolButton` at the configured size (`toolButtonHeightStrut`) whenever any tool button is placed in the row, so a row without one (no Android/Xcode project) is as tall as its neighbours and every row grows when the size goes to Large
- Which action bar items a row shows, their order and the tool buttons' size come from `RepositoryRowLayout` (Settings ▸ Repository Rows, `repositoryRowLayout` key, a JSON string in user defaults), read by the row with `@SharedReader`. Items (`RepositoryRowItem`) reorder only within their zone: menus & icons vs. the tool buttons (Android Studio, Xcode, Claude Code); the worktree create/delete and group remove buttons are fixed at the end. Decoding drops unknown items and appends ones a newer version added, so adding a case needs no migration. The type spells out `==`: as a `RawRepresentable` it would otherwise compare JSON strings. The size reaches `ToolButton` through AppUI's `toolButtonSize` environment value (`ToolButtonSize`; `.small` is icon-only)
- Each item is placed (`RepositoryRowItemPlacement`) in the row, in the "⋯" menu, or hidden (`hidden` / `inMoreMenu`, disjoint). Every item defaults to the row. The "⋯" menu (`RepositoryRowMoreMenu.swift`) is not an item: it is drawn at the end of the menus and icons only while an item is placed in it (`showsMoreMenu`), and lists those items in order, menus and icons first. In it the menus become submenus (`GitActionsSubmenu`, `YouTrackSubmenu`, `TuistSubmenu`, a disabled entry naming the running operation while one runs) and the buttons plain entries (`AndroidStudioMenuItem`, `XcodeProjectMenuItem`, `ClaudeCodeMenuItem`, the PR and pipeline titles taken from their buttons' tooltips, the approval one from `ApprovalStatusButton.headline`). A menu entry cannot present an alert or dialog, so each of those views' presenters is split out into a modifier (`gitActionsMenuPresentations`, `youTrackMenuPresentations`, `tuistPresentations`, `androidStudioPresentations`, `xcodeProjectPresentations`, `claudeCodePresentations`) that the in-row view applies to itself and the row applies on its action bar's background for the items placed in the menu only — a second presenter of the same state would fight the first
- Per-button Reducer+View pairs: `CreateWorktreeButton`, `DeleteWorktreeButton`, `TerminalButton`, `ClaudeCodeButton`, `XcodeProjectButton`, `TuistButton`, `TicketButton`, `ShareButton`, `WebButton`
- `TerminalLayoutReducer` / `TerminalLayoutView` / `TerminalPanelView`
- Two drag-to-reorder helpers, both `onDrag`/`onDrop` with a `public.text` payload for reasons documented in `ReorderableDrag.swift` (a `Section` header cannot be a `draggable` source, an undeclared UTType never matches a drop). `View.reorderable(payload:isEnabled:isTargeted:insertionEdge:onDrop:)` moves on release and draws an insertion line; the sidebar's repository group headers use it because sections under a `List` cannot slide. `View.liveReorderable(id:isEnabled:draggedId:onMove:)` (`LiveReorderableDrag.swift`) moves the dragged item on `dropEntered`, so the row animates around the pointer during the drag like browser tabs; the terminal tab pills use it. The dragged id lives in a `@State` shared by the row because a drop delegate cannot read the pasteboard synchronously. Reducers treat what arrives as untrusted: `repositoryGroupDropped` ignores a path that names no group, `terminalLayout(.moveTab)` ignores a session id that names no tab or a tab of another repository. Both apply the same rule, the dragged item takes the target's place, inside `withAnimation`
- Terminal notifications arrive two ways. `terminalSessionStatusChanged` entering `.waitingForInput` posts one worded from the program's OSC 7501 report (`TerminalProgramReport.notificationBody`: "Claude needs your permission: <its message>", "Claude is done."); `terminalNotificationReceived` (a program's OSC 9 / OSC 777) posts the program's own title and body, with the tab as subtitle, and leaves the session's status and `awaitsStartupPrompt` alone — status is the OSC 7501 reports' to set (before 2026-10-09 a notification also marked the session waiting, which swallowed the report's own notification that followed). Which of the two posts is the `terminalNotificationSource` setting's (Settings): `automatic` (default) drops a program notification marked `isFromStatusReportingProgram`, since Claude Code with its channel set to Ghostty sends both for one permission prompt and each would alert — the rule Wietty settled on, and the spec leaves OSC 9/777 to the host; `statusReports` drops every program notification; `programNotifications` posts none for reports, and a session leaving waiting still withdraws whatever was posted. Both use the session id as the notification identifier, so a later one replaces an earlier one, and `TerminalNotificationClient` spaces a tab's notifications out (ToolsIntegration README). Both skip posting when the `terminalNotifications` setting is off, or the tab is the panel's active one *and* the app is frontmost; leaving `.waitingForInput` withdraws the notification. A tab opened with a startup command posts nothing for its *first* `.waitingForInput` (`TerminalSession.awaitsStartupPrompt`): with `claude` as the startup command, that prompt is Claude having booted, and users open the next repository's terminal before it does. `onAppear` subscribes to clicks; `terminalNotificationTapped` opens the panel on that exact session (`openTerminal` then `activate`) and brings the app forward
- The terminal overlay takes **scoped stores**, never row values: `TerminalLayoutView.repositoryGroups` is `[StoreOf<RepoGroupReducer>]` and `activeRowStore` is resolved in `RepositoryListView`. TCA's `IdentifiedArray` observation compares element ids only, so a row handed over as a value freezes its counts at whenever the overlay last rebuilt — that was the stale push status in terminal view (2026-09-07). Store collections are wrapped in `Array(...)` because the sidebar is a `LazyVStack`
- Terminal tabs survive a relaunch (`TerminalTabArchive.swift`). `RepositoryListView` sends `saveTerminalTabsRequested` on `onDisappear` *and* on `NSApplication.willTerminateNotification` — quitting with the window open never takes it off screen, and closing the window releases the panes (hanging up their shells) before any quit. Each tab is saved with its shell's *current* directory (`TerminalViewStore.paneSnapshots()`, which reads it from the kernel with `proc_pidinfo(PROC_PIDVNODEPATHINFO)` on the shell pid — not OSC 7, which zsh only emits inside Terminal.app), the startup command it ran (stored verbatim: restore happens before the scan has placed the repo in a group, so settings can't be resolved yet), and which tab was on screen / remembered per repo. Failed tabs are not saved. A tab with Claude Code in its foreground is also saved with its conversation id (`TerminalPaneSnapshot.claudeSessionId`) and reopens typing `claude --resume <id>` instead of its startup command (`TerminalSession.commandToType`; `startupCommand` keeps the configured one for retries and the next save). The id comes from Claude Code's own per-process record, `<CLAUDE_CONFIG_DIR or ~/.claude>/sessions/<pid>.json` (`ClaudeSession`) — undocumented, so any surprise in it reads as "no session". Every process of the pty's foreground group is checked, but only one whose argv is Claude's (a stale record must not be pinned on a reused pid), and only a UUID is accepted, since it is typed into a shell. The file is written synchronously by `TerminalTabArchiveClient`, not `@Shared(.fileStorage)`, whose writes within a second of the last one wait on a timer that never fires at quit. `restoreTerminalTabs` (sent once from `onAppear`) drops tabs whose repository directory is gone and reopens ones whose own directory is gone at the repo root; the panel reopens only if it was open, otherwise the shells start when it is next shown. `didScanGroup` fills in the toolbar's button copies once the restored repo's row appears
- The toolbar's Xcode, Tuist and YouTrack buttons scope the opened row's own stores (`activeRowStore.scope(\.xcodeButton/\.tuistButton/\.youtrackButton, …)`), not copies in `TerminalLayoutReducer.State`. For YouTrack a copy would also go stale: after a transition the row refetches the ticket, and only that fetch knows the transitions now reachable. Hiding the panel sets `terminalLayout = nil`, and `ifLet` cancels that child's effects, so a generate running in a copy got its tuist process SIGTERMed with no error shown, and the row never knew it had run. Because the list stays mounted at opacity 0 under the overlay, both views then bind the same alert state; `presentsButtonAlerts` (environment in AppUI, so the YouTrackMenu package can read it; turned off on the hidden list) leaves the visible one as the only presenter. The Android Studio, web, ticket and git menu buttons are still copies, synced by `syncTerminalButtons`
- **Run tab**: the simulator pane's Run (`SimulatorPaneReducer.Delegate.runRequested`) opens a tab with `TerminalSession.runTitle` set (the scheme, shown on its pill instead of "Terminal N") whose startup command is the run script. A repository has at most one: running again replaces it in place (same position and number; dropping it from state hangs its shell up, which stops a build or app still running), so each run starts with a clean log, as in Xcode. Retrying a failed run tab runs its own command again, not the group's startup command. Run tabs are left out of `SavedTerminalTabs` — reopened at launch, they would build and launch the app again
- **Tab titles**: a tab is named by `TerminalSession.tabTitle` — the title its program set, else "Terminal N" (TerminalFeature README) — in the tab pill (cut at 200 pt, the whole title in the tooltip) and in a notification's location, which also names an only tab once it has a title. `terminalSessionTitleChanged` writes only a change: shell themes set the same title before every prompt. The title is saved with the tab (`SavedTerminalTab.title`, absent in older files) and shown on the reopened tab until its program sets another — a resumed Claude does once it is back up
- The terminal panel's "Simulator" toolbar button (shown for iOS repositories, or while the pane is open) toggles `SimulatorPaneView` to the right of the terminal container (`TerminalPanelView.terminalContent`). The container stays the `HStack`'s first child, so showing the pane only narrows the terminal — the one on screen: the container sizes only its visible pane, and hidden tabs keep their width until shown (`TerminalPaneContainerView`, see TerminalFeature's README). Its state is `TerminalLayoutReducer.State.simulatorPane`; visibility is an `appStorage` value, so it outlives the panel hiding. `RepositoryListReducer` subscribes to `SimulatorClient.activity()` on appear and shows the pane when a Claude in the *on-screen* repository's tab calls a simulator tool (`simulatorActivityReported`) — a call from another repository's tab acts on the simulator without moving the panel
