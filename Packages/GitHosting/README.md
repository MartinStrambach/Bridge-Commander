# GitHosting

GitHub/GitLab pull request + pipeline services.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- `PullRequestClient.fetchDetails` (the row's PR/MR for its branch) and `listOpen` (open PRs/MRs for the create-worktree dialog, `OpenPullRequests.swift`). `listOpen` includes PRs/MRs from forks (GitHub's `isCrossRepository`, GitLab's `sourceProjectId != targetProjectId`) as `isFromFork`, with the fork's owner. Their branch is not on `origin`, so they are checked out from `headRef` — the `refs/pull/<n>/head` / `refs/merge-requests/<iid>/head` that `origin` keeps for every PR/MR. A 200 with a null repository/project throws `.unauthenticated`, as the single fetch does, rather than reading as "no PRs". Each one carries `isAuthoredByViewer` (GitHub's `viewerDidAuthor`; on GitLab, which has no such field, the MR author compared with `currentUser` fetched in the same query), behind the dialog's "Only mine" checkbox (remembered in `worktreeOnlyMyPullRequests`). It filters the listed 50 locally, so an own PR older than the 50 most recently updated does not show
- `PullRequestDetails` is what `fetchDetails` returns for the row: URL, `PullRequestState` (draft / ready / merged / closed), pipeline, unresolved discussion count (`nil` = unknown, so the UI can tell it from 0), `ApprovalStatus` and `hasConflicts`. The two providers do not fill it equally: only GitLab reports a pipeline (`headPipeline`, its `path` made into a link; an unknown status maps to no badge rather than a guess) and conflicts (`conflicts`, or `detailedMergeStatus == CONFLICT`). A passing pipeline on a conflicting MR shows a warning icon, not a checkmark (`PipelineState.systemImageName(hasConflicts:)`). GitHub's unresolved count covers the first 100 review threads
- `ApprovalStatus` — `ApprovalDecision` (approved / changes requested / review required) plus who approved or asked for changes (`Reviewer`) and, where the provider has them, `approvalsRequired` / `approvalsLeft`. A tri-state rather than a fraction because GitHub never exposes a required-review count. On GitHub `reviewDecision` decides when present; it is null when no branch rule asks for a review, and then the reviews themselves decide, and the required count is 0 (`requiresNoApprovals`, which hides the row's approval slot) unless somebody has reviewed or been asked to. On GitLab the grouped counts (`groupedApprovalsRequired`/`groupedApprovalsLeft`) are preferred over the plain ones, which count a reviewer covering several rules more than once; `approvalsSatisfied` is derived from `approvalsLeft` for the same reason
- `Reviewer.avatarURL(pixels:)` asks the host for an avatar at the drawn size (`s=` on GitHub/Gravatar, `width=` on GitLab); `colorIndex` is an FNV-1a hash of the username, not `hashValue`, which Swift seeds per process and would recolour people on every launch
- `TokenVerificationClient` backs Settings' GitHub/GitLab token checks; the tokens are this package's `githubToken` / `gitlabToken` shared keys
