# GitHosting

GitHub/GitLab pull request + pipeline services.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- `PullRequestClient.fetchDetails` (the row's PR/MR for its branch) and `listOpen` (open PRs/MRs for the create-worktree dialog, `OpenPullRequests.swift`). `listOpen` includes PRs/MRs from forks (GitHub's `isCrossRepository`, GitLab's `sourceProjectId != targetProjectId`) as `isFromFork`, with the fork's owner. Their branch is not on `origin`, so they are checked out from `headRef` — the `refs/pull/<n>/head` / `refs/merge-requests/<iid>/head` that `origin` keeps for every PR/MR. A 200 with a null repository/project throws `.unauthenticated`, as the single fetch does, rather than reading as "no PRs". Each one carries `isAuthoredByViewer` (GitHub's `viewerDidAuthor`; on GitLab, which has no such field, the MR author compared with `currentUser` fetched in the same query), behind the dialog's "Only mine" checkbox (remembered in `worktreeOnlyMyPullRequests`). It filters the listed 50 locally, so an own PR older than the 50 most recently updated does not show unless the filter's search finds it
- `PullRequestClient.searchOpen` (`OpenPullRequestSearch.swift`) finds open PRs/MRs beyond the listed 50 for the dialog's filter. `OpenPullRequestQuery` reads the text: digits, `!12` / `#12` or a pasted PR/MR link name a number; text without whitespace is also tried as an exact source branch, because neither host's text search looks at branches (GitLab's `search:` covers title and description only, checked 2026-11-09); the rest is searched as text. It also holds the local match (`matches`) the dialog filters the listing with. One GraphQL request per search, its lookups switched on and off with `@include`: GitLab `mergeRequests(iids:)`, `(sourceBranches:)` and `(search:)`; GitHub `repository.pullRequest(number:)` (any state, so its `state` is checked for `OPEN`; a number that is an issue comes back null beside a `NOT_FOUND` error, which is fine) and two `search(type: ISSUE)` queries scoped `repo:… is:pr is:open`, one with `head:<branch>`. GitHub's variables are non-null in the schema, so a skipped lookup still gets a placeholder value; GitLab's are nullable and simply left out. Results come named first, then by branch, then by text, each PR/MR once (`uniqueByNumber`). GitHub ORs `repo:` qualifiers, so a `repo:` in the typed text would bring in other repositories' PRs; search hits whose `baseRepository` is not the searched one are dropped, since checking one out would take the same number or branch from this origin. GitHub's search returns no hits rather than an error for qualifiers it cannot read (`author:` of no user, a malformed `created:`, checked 2026-11-09). The author is matched only locally, against the listing
- `PullRequestDetails` is what `fetchDetails` returns for the row: URL, `PullRequestState` (draft / ready / merged / closed), pipeline, unresolved discussion count (`nil` = unknown, so the UI can tell it from 0), `ApprovalStatus` and `hasConflicts`. The two providers do not fill it equally: only GitLab reports a pipeline (`headPipeline`, its `path` made into a link; an unknown status maps to no badge rather than a guess) and conflicts (`conflicts`, or `detailedMergeStatus == CONFLICT`). A passing pipeline on a conflicting MR shows a warning icon, not a checkmark (`PipelineState.systemImageName(hasConflicts:)`). GitHub's unresolved count covers the first 100 review threads
- Merge trains (GitLab only): `PipelineStatus.isMergeTrain` comes from the pipeline's `mergeRequestEventType` (`MERGE_TRAIN` vs `DETACHED`/`MERGED_RESULT`), and `PullRequestDetails.mergeTrain` (`MergeTrainStatus`) from `autoMergeStrategy` (`MERGE_TRAIN` = on the train, `ADD_TO_MERGE_TRAIN_WHEN_CHECKS_PASS` = joins once its own pipeline passes). Only an MR on the train costs a second request, for `mergeTrainCar` (its position, and its pipeline, which then replaces the head pipeline). That one is separate and best effort because GitLab marks `mergeTrainCar` experimental (deprecated in introspection): were it removed, asking for it in the main query would fail the whole MR fetch. The fields in the main query (`mergeRequestEventType`, `autoMergeEnabled`, `autoMergeStrategy`) are stable (checked against gitlab.com introspection, 2026-11-02). A train pipeline in progress draws a tram (`PipelineState.systemImageName(hasConflicts:isMergeTrain:)`); a finished one keeps the result icon, so a failed train still reads as failed
- `ApprovalStatus` — `ApprovalDecision` (approved / changes requested / review required) plus who approved or asked for changes (`Reviewer`) and, where the provider has them, `approvalsRequired` / `approvalsLeft`. A tri-state rather than a fraction because GitHub never exposes a required-review count. On GitHub `reviewDecision` decides when present; it is null when no branch rule asks for a review, and then the reviews themselves decide, and the required count is 0 (`requiresNoApprovals`, which hides the row's approval slot) unless somebody has reviewed or been asked to. On GitLab the grouped counts (`groupedApprovalsRequired`/`groupedApprovalsLeft`) are preferred over the plain ones, which count a reviewer covering several rules more than once; `approvalsSatisfied` is derived from `approvalsLeft` for the same reason
- `Reviewer.avatarURL(pixels:)` asks the host for an avatar at the drawn size (`s=` on GitHub/Gravatar, `width=` on GitLab); `colorIndex` is an FNV-1a hash of the username, not `hashValue`, which Swift seeds per process and would recolour people on every launch
- `TokenVerificationClient` backs Settings' GitHub/GitLab token checks; the tokens are this package's `githubToken` / `gitlabToken` shared keys
