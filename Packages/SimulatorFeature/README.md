# SimulatorFeature

The iOS simulator pane beside the terminal, and the MCP server that lets Claude Code in the app's terminals see and drive it — the counterpart of Claude Desktop's simulator pane.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

**Research order for simulator behaviour.** Before reverse-engineering CoreSimulator, HID or DeviceHub (`strings`, `otool`, disassembly), look for prior art:
1. idb: `gh search code <symbol> --repo facebook/idb`, starting in `FBSimulatorControl/`.
2. AXe (`github.com/cameroncooke/AXe`).

Both are MIT, and this code follows them. In 2026-10, about 76 disassembly calls on the DeviceHub plugin went into decoding the iPhone Duo's hinge report, which idb's `SimulatorHingeAngle` already had.

## Notes

- **Everything goes through Apple's private CoreSimulator, in this process.** `SimulatorHost` `dlopen`s `/Library/Developer/PrivateFrameworks/CoreSimulator.framework` (allowed under the hardened runtime: it is Apple-signed) and messages it through `ObjCRuntime` — there are no headers, and most of its objects are `ROCKRemoteProxy`s that answer `respondsToSelector:` but not KVC, so properties are read by sending getters (`value(forKey:)` throws). Claude Desktop instead runs Meta's FBSimulatorControl in a sandboxed helper process; in-process is what lets the pane show the framebuffer `IOSurface` with no copy or encode, at the cost of a CoreSimulator crash taking the app with it. Expect breakage on Xcode majors; idb (`github.com/facebook/idb`, `FBSimulatorControl/`, MIT) tracks those changes and is the reference this code follows
- **Switching or updating Xcode swaps CoreSimulator under the running app.** Every Xcode shares the one framework in `/Library/Developer/PrivateFrameworks`, and `xcode-select` to another Xcode (27.0 RC ↔ 27.1 RC here, 1171.7 ↔ 1174.9.2) can install its version over it. The copy already loaded then cannot reach the new CoreSimulatorService ("CoreSimulator.framework was changed while the process was running", in `~/Library/Logs/CoreSimulator/CoreSimulator.<bundle id>.log`), and `-[SimDeviceIOClient ioPorts]` raises an `NSInternalInconsistencyException` instead of returning nil — which, thrown through Swift frames, aborted the app (2026-10-08). So `SimulatorHost` records the version it loaded and, before each use, compares it with the `Info.plist` on disk: once they differ, every call fails with `coreSimulatorChanged` ("restart Bridge Commander"), since a loaded framework cannot be unloaded. Calls known to raise go through `ObjCRuntime.catchingException`, backed by the Objective-C `ObjCExceptionCatching` target (`@try`/`@catch`; Swift cannot catch an `NSException`), for the race where the swap lands between the check and the call
- **Input goes to `dtuhidd`, not the legacy Indigo HID client.** From CoreSimulator 1155.4 (Xcode 27) the guest drops the Indigo messages `SimDeviceLegacyHIDClient` sends — delivered byte-correct, silently ignored. `SimulatorHIDConnection` looks up `com.apple.coredevice.feature.remote.hid.digitizer` in the simulator's bootstrap namespace (`-[SimDevice lookup:error:]`), wraps the port with the private `xpc_endpoint_create_mach_port_4sim`, marks the connection `xpc_connection_enable_sim2host_4sim` (without it the daemon sees the peer but no payloads), and sends plain XPC dictionaries: `IndigoDigitizerEvent` (normalized point, phase 0/1/2 = began/moved/ended), `IndigoKeyboardButtonEvent` (HID keyboard usage), `IndigoButtonEvent` (Consumer-page usage: home 0x40, lock 0x30). `HIDButtonState` is 1-based (down 1, up 2); 0 is rejected. The daemon is demand-launched and aborts early in a boot, and a send to it never fails, so a barrier is round-tripped (with retries) before a connection is used. Older CoreSimulators are refused (`unsupportedCoreSimulator`) rather than given the Indigo path, which nobody here can test
- **Screen**: the main display is the `SimScreen` port descriptor whose `displaySize` equals the device type's `mainScreenSize` (devices also list external/CarPlay screens; an open iPhone Duo shows its inner panel instead, see Fold). `SimulatorScreenView` sets the surface as its layer's `contents` and registers `registerScreenCallbacksWithUUID:callbackQueue:frameCallback:surfacesChangedCallback:propertiesChangedCallback:` on its own serial queue (CoreSimulator delivers with `sync` onto it, so the callbacks only hand off). The surface object is the same every frame, so reassigning it does nothing; the per-frame refresh is `-[CALayer setContentsChanged]` (private; WebKit uses it), coalesced to one per main-loop turn. Screenshots read `framebufferSurface` through Core Image, turned upright (see Rotation) and scaled to points, so an image pixel is a tool coordinate
- **The pane's screenshot button** saves a PNG at the native pixel size, turned upright like the tool's screenshots but not scaled to points, where Simulator.app's File ▸ Save Screen would: its own `ScreenShotSaveLocation` (`com.apple.iphonesimulator` defaults), else the system's `com.apple.screencapture` `location`, else the Desktop, named as Simulator.app names them ("Simulator Screenshot - <device> - <date> at <time>.png", numbered when the name is taken). Location and name logic is pure (`SimulatorScreenshotFile`) and tested
- **Mouse and keys in the pane**: click/drag/up are touch began/moved/ended; a two-finger trackpad scroll drags a finger (momentum ignored — the guest flings on its own); keys are mapped by `SimulatorKeyboardMap` (US layout), and ⌘-combinations are left to the app's shortcuts. Input runs on one ordered `Task` chain so a drag cannot overtake its touch-down
- **Multi-touch** is the same `IndigoDigitizerEvent` with a second contact, `pointTwo`; a gesture keeps one finger count from began to ended. In the pane, as in Simulator.app: ⌥-drag pinches/rotates with the second finger mirrored across the screen's centre, ⌥⇧-drag moves both fingers together, and two dots show the fingers while ⌥ is held. A trackpad pinch (`magnify`) and rotation (`rotate`) drive two fingers about the pointer; they share one contact that lifts when the last of them ends. Tools: `pinch` (centre, scale, optional rotation) and `two_finger_drag`; `SimulatorHost.pinchFingers` starts or ends 60 pt apart so both directions use a comfortable spacing
- **Accessibility tree** (`SimulatorAccessibility`, the `describe_ui` tool): the private AccessibilityPlatformTranslation framework, as Accessibility Inspector uses it — not idb's injected `SimulatorFrameworkBridge`, which Claude Desktop ships. `AXPTranslator.sharedInstance` gets a bridge-token delegate (`AccessibilityBridgeDelegate`, `@objc` methods named for `AXPTranslationTokenDelegateHelper`, the protocol added at runtime) that answers each lazy attribute read by sending the request into the simulator with `-[SimDevice sendAccessibilityRequestAsync:completionQueue:completionHandler:]` and blocking (5 s cap) for the reply. `frontmostApplicationWithDisplayId:bridgeDelegateToken:` / `objectAtPoint:displayId:bridgeDelegateToken:` give a translation object, `macPlatformElementFromTranslation:` an `NSAccessibilityElement` read with the ordinary accessors; frames come back in screen points. The translator is a non-thread-safe singleton, so all of it runs on one serial queue. The token is the device's UDID and is never unregistered: the translator caches elements under the token of the request that first produced them, and a per-request token dropped afterwards made every later read return an empty tree (found 2026-10-07). `SimulatorAccessibilityFormatter` leaves out containers with no label/value/identifier that are not controls, so the model gets the screen's content, not its view hierarchy. Walks are capped at 1500 nodes / depth 40
- **Accessibility actions** (`press_element`, `set_value`, `scroll_to_element`) find an element by identity rather than position: `SimulatorElementQuery.match` is a pure function over the flattened tree (exact identifier, then exact label, label ignoring case, label containing the text; the application element excluded; among several matches of a tier the action's preferred roles — controls for a press, text fields for a value — win; `index` picks among the rest, and a miss or an ambiguity lists the candidates so the model can refine). `SimulatorAccessibility.perform` walks, matches and acts in one turn of the work queue, on the live `NSAccessibilityElement` the walk read, so a screen that changes between a walk and an action cannot redirect it. Verified on Xcode 27 / iOS 27 Settings (2026-10-07): `accessibilityPerformPress()` navigates, `setAccessibilityValue(_:)` fills the search field (and reads back), `performScrollToVisible` scrolls a row out from under the bottom search bar. iOS lists `AXPress` on nearly every element and the translator returns `true` even for static text, so a press "succeeding" says nothing about its effect; the fallback to a HID tap on the element's activation point (its centre, or a wide switch's trailing end) only fires when `AXPress` is missing or returns `false`. Only elements in the tree can be found, and lists expose just their on-screen rows — scrolling to a row further down still needs a swipe
- **`ObjCRuntime.object` is only for methods that return an object.** Calling a `void` method through it makes Swift retain whatever is in the return register — `setBridgeDelegateToken:` crashed the app with `EXC_BAD_ACCESS` in `swift_unknownObjectRetain`. Use `ObjCRuntime.send` for those
- **Action tools wait for the screen to settle** (`wait_for_settle`, default true — the coordinate tools, keys and buttons, and the element tools, which take their baseline before the element is looked up) and say how it went — "Screen settled after 880 ms.", "No change on screen within 600 ms …", "Screen still changing after 3000 ms …" — so the model's next screenshot shows the result, not the old screen or an animation midway. `ScreenFingerprint` reads the framebuffer `IOSurface` under a read-only lock (no Core Image): a grid of ~48-pixel cells (16 pt at 3×), each the mean byte sum of every 3rd pixel of every 4th row — ~0.7 ms optimized, ~2 ms in Debug, whose loops are written for `-Onone` (with `for`/arrays it took ~400 ms). `SimulatorHost.waitForScreenToSettle` polls every 40 ms, reusing the surface between polls (fetching it is an XPC round trip of up to 100 ms while the simulator animates) and re-fetching every 8th. `ScreenSettleDetector` (pure, unit-tested) compares each fingerprint with the last one that counted as a change: settled after 300 ms with no change; unchanged if nothing changed within 600 ms (a cold app took 400 ms to start responding); still changing at 3 s. A change needs more than 4 cells to move by more than one unit of their mean, which ignores a blinking caret (it fades, ~150 ms twice a second, over 2–3 cells) at the price of missing a change as small as a lone checkmark. The baseline is taken before the action, so a change that began during `drain()` still counts. Measured on an iPhone 18 Pro (2026-10-07): navigation push/pop 0.8–1.0 s, app launch 0.85–0.95 s after `simctl launch` returns, typing into search 0.8–1.3 s, home-screen jiggle mode times out as still changing. An app that reacts only after a pause longer than the quiet period (the first keyboard of a fresh simulator: highlight, then 750 ms of nothing, then the transition) is reported settled too early
- **MCP server** (`SimulatorMCPServer`): HTTP/1.1 on `127.0.0.1`, port 47615 (release) / 47616 (debug, by bundle id) so both builds can run, falling back to any free port. Streamable-HTTP without the optional SSE stream: POST `/mcp`, one JSON response per request, 202 for notifications, 405 for GET/DELETE. Requests with any `Origin` header or a non-loopback `Host` are refused — those are a browser page (cross-site, sandboxed frame, DNS rebinding); local processes are not defended against, since they can already run `simctl`
- **How a pane's `claude` finds it**: `ClaudeCodeRegistration` adds one user-scope server (`claude mcp add-json --scope user bridge-commander-simulator …`, run from the pane's "Connect" banner) whose `url` is `${BC_SIMULATOR_MCP_URL:-http://127.0.0.1:47615/mcp}` and whose `X-Bridge-Commander-Session` header is `${BC_TERMINAL_SESSION_ID:-none}`; Claude Code expands both when it loads the config. `RepositoryListView` builds its `TerminalViewStore` with `additionalEnvironment` returning `SimulatorMCPServer.terminalEnvironment(sessionId:repositoryPath:)`, so every pane starts with its own values; the server notes each session's repository as it hands them out (every shell, restored tabs' included, starts through it), which is how a call is tied to a repository's device without the registered config carrying the path. A `claude` outside the app reaches the release app if it runs, and otherwise lists the server as failed. Verified end to end with `claude -p --mcp-config` (2026-10-07)
- **Device choice is per repository (worktree)**, so one terminal can work on an iPhone while another works on an iPad. `SimulatorHost` keeps each repository's device in `UserDefaults` (`simulatorSelectedDeviceUDIDByRepository`) plus the last one chosen anywhere (`simulatorSelectedDeviceUDID`), which a repository with no choice of its own starts on and a `claude` outside the app uses. The pane and the tools of that repository's terminals share it: the server gives each call `LiveSimulatorToolActions` scoped to the calling session's repository. A tool call without a `udid` uses the repository's device if booted, otherwise a booted one no other repository has chosen (else any booted one) — and makes it the repository's, so the pane follows the simulator Claude booted. Each device-touching call is published (`SimulatorActivity`); `RepositoryListReducer` opens the pane for the calling session's repository (the one on screen for a `claude` outside the app) without switching the panel to it, and the pane only moves its shown device when the call came from the repository it is showing
- **The pane is shown per repository**: `visibleRepositoryPaths` (`simulatorPaneRepositoryPaths` in `UserDefaults`) lists the repositories and worktrees whose terminal has it open. There is still one pane state — device list, banners — beside whichever repository is on screen: the view's `.task(id: repositoryPath)` sends `.task(repositoryPath:)`, which restarts the polling for that repository's device. The visibility actions carry the repository path, and the pane learns it from the view rather than from the layout state, because `RepositoryListReducer` changes the active repository directly on the layout state
- Booting/shutting down shell out to `xcrun simctl` (headless — no Simulator.app window). The pane polls the device list every 1.5 s while visible, since `simctl` in a terminal changes it too
- **Crash reports** (`CrashReports/`, the `list_crashes` and `crash_report` tools): simulator processes crash into the host's `~/Library/Logs/DiagnosticReports` as ordinary `.ips` files (a one-line JSON header, `bug_type` 309 for a crash, then the JSON report). The device is identified by `coalitionName` = `com.apple.CoreSimulator.SimDevice.<UDID>`, present on every simulator report; `procPath` contains `CoreSimulator/Devices/<UDID>/` only for installed apps (`…/data/Containers/Bundle/Application/…`) — the runtime's own processes are anonymised to `/Volumes/VOLUME/*/…`. Those (PosterBoard, intelligence daemons) crash constantly in iOS 27 runtimes — hundreds of reports here — so the list hides them unless `include_system` or a `bundle_id` asks. Simulator reports carry no `asi`: an uncaught exception's reason or a Swift `fatalError` message exists only in the device's log, so `crash_report` runs `simctl spawn <udid> log show` pinned to the crashed pid and the minute before the capture time (about 2 s; nothing when the device is shut down). Use the report's `captureTime`, not the file's mtime — old reports get their mtime bumped days later (seen: a 2026-10-01 crash with a 10-07 mtime), so mtime only pre-filters. `Retired/` is ignored. Parsing and formatting are pure and tested with fixture strings; `SimulatorCrashReportSource` is the seam over the folder and the log. Verified 2026-10-07 against real crashes (uncaught `NSRangeException`, `fatalError`, null write) of a test app on an iOS 27 simulator
- **Rotation** (`SimulatorHost+Rotation`, the `rotate` tool, the pane's rotate buttons; found 2026-10-07 on CoreSimulator 1171.7 / iOS 27 with iPhone Air):
  - *Writing*: a GSEvent `DeviceOrientationChanged` (type 50 | host flag 0x20000) sent as a raw 108-byte Mach message (id 0x7B, value at 0x4C) to SpringBoard's `PurpleWorkspacePort`, looked up with `-[SimDevice lookup:error:]` — what Simulator.app's `sendPurpleEvent:` does. The value is `UIDeviceOrientation`'s number (3 makes the guest report `landscapeLeft`, top of the device on the left); idb names it by interface orientation instead, hence its "swapped" `physicalPurpleOrientation`. idb's newer route — an `orientation-picker-control` report (`IndigoVendorDefinedEvent`, page 0xff61 usage 0x5b) on `dtuhidd`'s `com.apple.coredevice.feature.remote.hid.vendordefined` — is accepted and ignored here: idb uses it only when the CoreDevice `querymotioncapabilities` action reports `deviceMotionState`, which these runtimes report `false` — except the iPhone Duo's iOS 27.1 runtime, where it is the only thing that turns the interface (see Fold)
  - *Reading the device*: the guest's `com.apple.coredevice.feature.remote.devicecontrol.orientation` service, same XPC envelope as `dtuhidd` (`messageType` `OrientationRequest`, payload `{currentOrientation: {}}`), answers `currentDeviceOrientation` — `unknown` until the device is first turned after boot, so `currentDeviceNonFlatOrientation` is the fallback. (The CoreDevice `displayinfo` action on `com.apple.coredevice.feature.getdisplayinfo` reports the same plus each display's `currentOrientation` `rot0/90/180/270`, but needs the CoreDevice request envelope; not used.)
  - *Reading the interface*: `-[SimScreen screenProperties]` (an immutable proxy) has `uiOrientation`: 1 portrait, 3 interface turned clockwise (device landscape right), 4 counterclockwise (landscape left); 2 is assumed upside down. It follows the *interface*, not the device: the iPhone home screen and portrait-only apps keep 1 while the device turns, and Face ID iPhones never turn upside down (Safari stayed at 3 with the device upside down). The screen's properties-changed callback delivers the same object when it changes, which is how the pane turns at once. `SimulatorDevice.rotation` is read from it, so everything below follows the interface — the space the user and the model see
  - *Coordinate spaces*: the framebuffer `IOSurface` stays 1260×2736 (portrait) in every orientation, the app drawn sideways into it; the `dtuhidd` digitizer takes points normalized to the portrait panel (a tap at the framebuffer-normalized position hit the control, also in landscape); accessibility **frames** come back in the interface's space (Safari in landscape: `Application frame=(0,0,912,420)`), but **hit-testing** (`objectAtPoint:`) takes panel points. So the tools take and give interface points, origin top left, and `SimulatorScreenRotation` (pure, tested; idb's `SimulatorDisplayGeometry` transforms) turns them into panel space on the way to the digitizer and the hit test; screenshots are the framebuffer turned upright (`CIImage.oriented`, `.left` for counterclockwise) and then scaled to points. `list_devices` and `screenshot` report the rotated size. The pane shows the surface in a sublayer turned about its centre (a flipped view, so a positive angle is clockwise), keeps clicks, drags and finger indicators in the interface's space, and turns them into panel space as touches are sent. Rotating does not change the pane's width (2026-10-09): the screen fits itself inside at `displayedPixelSize`'s aspect, so a landscape screen is shorter rather than the terminal narrower. The width is the one dragged at the pane's leading edge (`simulatorPane.width` in `UserDefaults`, one for every repository and device), else — before any drag, or after a double-click on the edge — what fits the device held portrait (`portraitRotation`) at the available height, at most half the panel; always leaving the terminal 320 pt
  - `rotate` waits until `uiOrientation` reaches the orientation's interface rotation plus 0.5 s for the animation, or gives up after 1.5 s (the app does not support it) and says so — the tool in its reply, the pane's rotate buttons in a notice (`SimulatorRotation.interfaceFollowed`), since the device does turn and the next tap goes on from there, so a silent button seemed broken. Upside down could only be checked not to turn the interface (iPhone); its transform is idb's, unverified live
- **Fold (iPhone Duo)** (`SimulatorFold`, `SimulatorHost+Fold`, the `set_fold` tool, the header's Fold/Unfold button and the More menu's Hinge items; found 2026-10-08 on Xcode 27.1 RC, CoreSimulator 1174.9.2, iOS 27.1):
  - *The device*: `SimDeviceType.iPhone-Duo` (iPhone19,4, iOS 27.1+) lists two `integrated` displays in `-[SimDeviceType capabilities].capabilities.displays`, readable without booting: screen 1, the cover (1398×2034 px @3x, the main screen), and screen 3, the inner panel (2007×2853 px @3x, `nativeRotation` 270, so its interface reads `uiOrientation` 3, landscape). `SimulatorFoldDisplays` (pure, tested) takes the two; a device type with one is not foldable (`SimulatorDevice.fold` nil)
  - *Folding*: Simulator.app is gone in 27.1; DeviceHub's hinge slider (`DeviceKit.framework/PlugIns/CoreDevicePopDeviceKitExtension.devicekitplugin`) sends a vendor-defined HID report through `CoreDevice.HIDVendorDefined`, as idb's `SimulatorHingeAngle` (MIT) does: usage page 0xFF61, usage 0x5B, version 0, data an `IOCFSerialize(_, kIOCFSerializeToBinary)` dictionary `{provider: com.apple.Virtualization.VirtualMachines, source: hinge-slider-control, type: range, value: 0…180}` (`SimulatorDeviceStateReport.hinge(angle:)`). It goes to `dtuhidd`'s `com.apple.coredevice.feature.remote.hid.vendordefined` in the usual envelope (`IndigoVendorDefinedEvent`). It must be a plain message: sent with `isBarrier` true it is answered but never dispatched. `SimulatorHIDConnection.sendVendorDefinedReport` round-trips a barrier first (the daemon is up), sends the report, then another barrier (delivered). Reports go through `SimulatorHost.sendDeviceState`, one at a time per device, on one connection kept for the device (see *A slow `dtuhidd`*); the guest keeps the angle when a connection closes. The guest's `locationd` (`CMDeviceStateRelayManager`, log category `com.apple.locationd.Motion:DeviceState`: "Angle value set to", "propertyB" 1 closed / 2 partly open / 3 flat) relays it to SpringBoard, which moves the interface to the cover at 0 and to the inner panel as the hinge opens — a single report of 130 from closed does it, as 180 does; from open, 130 keeps the inner panel. Three states are offered: closed (0), open (180) and partially open (130, where DeviceHub's partial unfold leaves the hinge: it sweeps there in ~30 reports over 0.6 s, but one report does the same; `locationd` reports it as partly open, `propertyB` 2, so apps see a half-open device on the inner panel). The header button toggles closed ↔ open (a partially open device closes); the More menu's Hinge submenu sets any of the three
  - *Which panel shows* is not readable: both screens keep `powerState` 1 and their `backlight.state` (2 cover, -101 inner) in either state, the unused one is merely black, and the guest's orientation service says nothing about the hinge. So the state is the one last set from here, stored per boot in user defaults (`simulatorOpenFoldableDevices`: per UDID, the `lastBootedAt` it was set in and the `SimulatorFold`; `bootSessionUUID` is nil) — a fresh boot starts closed, and a fold made in DeviceHub is not seen. Each `devices()` read refreshes an in-memory map of open panels for the calls given only a UDID (the pane's screen attachment, rotation); calls given a `SimulatorDevice` go by its `screenID`
  - *The inner panel*: when open or partially open, `SimulatorDevice` describes it — `screenPixelSize`/`screenScale` are the panel's, `screenID` 3, `rotation` from its `uiOrientation` — and the screen is the `SimScreen` of that size. Touches need the digitizer `target` set to the screen ID (target 0 does not reach it); the point is normalized to the portrait panel as usual. Accessibility calls need `displayId` 3 too (with 0 the tree is still the inner panel's, but `objectAtPoint` finds nothing); apps' frames come back in the interface's space as on the main screen, but SpringBoard's (the home screen, recognised by its unlabelled application element) come back in the panel's native portrait space and are turned (`SimulatorAccessibilityDisplay`), and the application element's own frame (the cover's size for SpringBoard) is replaced by the screen's. Recordings pass `--display=3` and stay on the panel they started on
  - *Rotating*: the Purple GSEvent alone changes what the guest's orientation service reports but not the interface, on either panel; SpringBoard follows only DeviceHub's other control, the orientation picker — the same report with `source: orientation-picker-control`, `type: enum`, `value` `portrait` / `pud` / `landscape-left` / `landscape-right` (`SimulatorDeviceStateReport.orientation`), which `devicectl device orientation set` does not send (it changed nothing). So a device that folds gets both, the event keeping the orientation service, which the pane's rotate buttons read, in step. Two catches, both measured: a report on a connection closed as soon as its barrier is answered was dropped every time, one held 0.3 s never (one reason the connection is now kept); and SpringBoard defers orientation changes while it moves the interface between the panels, dropping about half the rotations sent right after a fold, so `setFold` returns 1 s after the screen settles. The inner panel is mounted turned (`nativeRotation` 270): held portrait the device shows it landscape (`uiOrientation` 3), and every orientation one quarter turn clockwise on from the cover's — landscape left shows it portrait-shaped (`SimulatorFoldDisplays.Panel.portraitRotation`, `SimulatorDevice.interfaceRotation(for:)`, which `rotate` waits for and reports against)
  - *A slow `dtuhidd`*: the daemon builds a set of virtual HID services (buttons, keyboard, the touchscreens) for every connection, one connection at a time — 0.5 s at best, and it can stall while the guest is busy: once, 3 s after closing, while PosterBoard restarted its poster extensions, creating the first service took 12.6 s. Reports used to go on a connection each, held 0.5 s and dropped after a 4 s barrier timeout, then retried on a new one; in use (rotate and fold buttons in a row) those connections queued behind each other in the daemon and were closed by the time it reached them, so reports were lost and taps seemed to do nothing. Now one vendor-defined connection per device is kept (`SimulatorHost.sendDeviceState`), reports wait for the one before, a barrier is waited for up to 30 s on the same connection, and only an XPC error (no daemon yet, or it restarted) makes a new one. Checked live (2026-10-08): ten folds and rotations in a row on one connection, all delivered, 0.5–3.3 s each. The pane shows a fold as a transition (spinner, other controls hidden) until it is done. `dtuhidd`'s log names each connection's client (`hid.vendordefined.peer[<pid>]`), which is how this was traced
  - *DeviceHub fights back*: while DeviceHub shows the device it monitors the hinge and, seeing it change, may sweep its own slider's angle back in (seen 2026-10-08: interpolated reports from DeviceHub's pid seconds after one from here). Close DeviceHub's window for the device when folding from the pane
  - *Closing* carries the frontmost app over to the cover. Once (from the home screen, not reproduced) it locked the device instead: the cover went to the always-on state ("InactiveOn", Flipbook) showing a stale frame that ignored touches and Home; the side button woke it and a swipe up unlocked it, which the tool's description tells the model
- **Header and run bar fit any pane width** (`ViewThatFits`, 2026-10-08): the header's icons step down from all of them, to Home / Record / Shut Down with screenshot and rotation moved into the More menu, to only More (plus a running recording's stop button), and last the device's name truncates; the run bar drops Run and Stop's titles, then truncates the scheme's name. Names truncate only in the last variant because a borderless `Menu` without `fixedSize` stretches to the width offered, leaving its chevron away from the text. Even the full header has no room for more icons at the pane's usual width — Lock left it for the More menu's Side Button, which sends the same usage — so new controls go in the More menu. The exception is Fold/Unfold (2026-10-08), shown only for a foldable device, whose pane is wider (the Duo's cover is 1398×2034 px against an ordinary iPhone's ~1206×2622); it stays in the full and compact headers and leaves for the More menu's Hinge submenu, always there, in the minimal one
- **Buttons** (`SimulatorHardwareButton`, Consumer-page usages on `dtuhidd`, as idb's `SimulatorHIDButtonIdentity`): `side_button` is the same physical button and usage as `lock` (Power, 0x30), kept as its own name because that is what models and people ask for on Face ID iPhones; `play_pause` is 0xCD. **There is no Apple Pay**: `dtuhidd` has no usage for it, and idb found that two side-button presses lock and wake the device instead of bringing up Wallet — only the legacy Indigo path, which these runtimes ignore, had a source for it. `press_button` takes `duration_ms` (default 100) for long presses. The pane shows Home as an icon; side button (lock), Siri, volume and play/pause are in its "More" (⋯) menu
- **Key sequences**: `press_key` takes `keys` (an array) as well as `key`. Every name is parsed before any key goes down, so a typo does not leave a sequence half done; `SimulatorHost.press(device:keys:)` presses them in order and drains once. Checked live (2026-10-08): `["cmd+a", "delete"]` empties Maps' search field
- **Ideas from AXe** (`github.com/cameroncooke/AXe`, MIT; a CLI over idb's HID) — switches, values, waiting, sliders, presets, batches and hold-to-drag, checked live on iOS 27 Settings and SpringBoard (2026-10-08):
  - *Switches*: the translator turns a `UISwitch` / SwiftUI `Toggle` into an `AXCheckBox` (subrole `AXSwitch`), reported as `Switch` so `role: "Switch"` finds it. Its frame is the whole row (330 pt in Settings), and a tap on the row's centre does nothing; 31 pt in from the trailing edge toggles it (AXe's numbers). `SimulatorAccessibilityNode.activationPoint` gives that point for a switch wider than 100 pt, `describe_ui` prints it as `tap=(x,y)`, and `press_element`'s fallback taps there. AXPress toggles switches anyway; one pressed while half off screen during a transition (Smart Invert, which redraws everything) reported success and did nothing. Right-to-left layouts are not handled
  - *Values*: `current_value` matches `value=` in the same three tiers as the label, tried after it (`SimulatorElementQuery.matches`, which `match` and `wait_for_element` share)
  - *Waiting*: `wait_for_element` re-reads the tree every 300 ms until the query matches (or, with `gone`, stops matching); the element tools' `timeout_ms` retries their action on `notFound` (`SimulatorElementTools.untilFound`), retaking the settle baseline before each attempt so a screen that finished loading meanwhile is not taken for the action's effect
  - *Sliders* (`set_slider`, `SimulatorSliderTool`): `setAccessibilityValue` is accepted and ignored though the slider reports its value settable, and the frame is not the track (the Dynamic Type slider's is its 362 × 80 pt row, "A" icons included; the thumb at 0 % sat 48 pt in). Dragging first went wrong: a rightward drag that starts left of the thumb is the back swipe and left the page. So it steps with AXIncrement / AXDecrement first (no touch; exact on a stepped slider, within half of the 10 % increment on a continuous one, stepping back once if a step overshoots), then drags the rest from where the thumb should be — too short and slow to complete a back swipe — re-measuring the track from how far the value moved (`SimulatorSliderTrack`, only from moves of 5 % or more). A slider that vanishes after a drag is reported as such. Values parse from "50 %", "%50", "0.3" (`SimulatorSliderValue`); a value with letters ("3 stars") cannot be checked and is refused. Vertical sliders are not handled
  - *Presets* (`gesture`, `SimulatorGesturePreset`): named for what a scroll reveals (`scroll_down` moves the finger up), since AXe's finger-named `scroll-up` reads backwards. Edge swipes start 2 pt in. `swipe_from_left_edge` went back in Settings
  - *Batches* (`batch`, `SimulatorBatchTool`): each step is an ordinary `SimulatorMCPTools.call`, so it settles as its tool does; every step is checked before any runs, a failure stops the rest unless `continue_on_error`, and screenshots taken by steps come back as images after the report. Nested batches and device or crash tools are not steps
  - *Hold-to-drag*: `swipe`'s `hold_ms` keeps the finger still that long before moving and as long on the end before lifting (drop targets that react to hovering). On the home screen it picked an icon up and carried it — and dropped onto another icon's centre it made a folder. Out of an open folder it never worked: the long press opens the icon's menu below it, so a downward move slides over the menu, and neither an upward move nor jiggle mode lifted the icon
- **Memory warning** (`simulate_memory_warning`, the More menu): `-[SimDevice simulateMemoryWarning]` in-process, as Simulator.app and idb do — a `void` method, so `ObjCRuntime.send`. Checked live on iOS 27 (2026-10-08): the guest logs "Scene received memory warning" for every scene
- **Location** (`set_location`, the More menu's Location submenu, which also offers fixed places — `SimulatorLocationCommand.places`, Prague's Old Town Square for now): `xcrun simctl location` (`set`, `start` for waypoints with `--speed`, `run <scenario>`, `clear`), not `SimDevice`'s `SimLocation` methods: routes take waypoints in an undocumented shape there, and simctl validates and encodes them, at the cost of a ~0.2 s process launch on a rarely changed setting. `SimulatorLocationCommand` builds the arguments (pure, tested; coordinates with `String(format:)`, so "." whatever the locale). The scenarios listed (`knownScenarios`) are what the iOS 27 runtime lists; `simctl location <udid> list` names the runtime's own, and an unknown one comes back as simctl's error. Checked live in Maps (2026-10-08): set, route, scenario and clear all take
- **Screen recording** (`SimulatorScreenRecorder`; `start_recording`/`stop_recording`, the pane's record button):
  - `xcrun simctl io <udid> recordVideo --codec=h264 <file>` — what Simulator.app's File ▸ Record Screen runs — rather than an `AVAssetWriter` fed from the framebuffer. simctl prints "Recording started" on stderr once it runs (start waits up to 10 s for it) and writes the file only when sent **SIGINT** ("Wrote video to: …" on stdout); `terminate()` would leave nothing. H.264, not simctl's default HEVC, so the file plays and uploads anywhere. The result is native pixels of the portrait framebuffer (1206×2622 on an iPhone 17 Pro, checked 2026-10-08); a landscape recording is untested and presumably sideways
  - One recording per device. Each is capped at 10 minutes (`defaultLimit`) and every running one is interrupted on `NSApplication.willTerminateNotification` (up to 3 s for simctl to write), so a forgotten recording neither grows without end nor outlives the app as an orphan `simctl`. A crash of the app still orphans it
  - A recording that ends on its own — the limit, or simctl quitting because the device shut down (the termination handler) — is kept in `ended` and reported by the next `stop`, so `stop_recording` after the limit says where the file went instead of "not recording". `stop_recording` without a `udid` stops the only recording running, else the repository's device's; it does not need the device booted, and neither does the pane's stop button
  - Files go where screenshots do (`SimulatorScreenshotFile.defaultFolder`), named as Simulator.app names recordings. A model-given `path` may be a folder or a `.mov` file (".mov" is added when there is no extension); an existing file, a relative path or another extension is refused rather than overwritten or mislabelled (`destination`, pure, tested)
  - The pane follows recordings Claude starts and stops through `recordingDeviceIdChanges()`, a stream that yields the current set at once and on every change
- **Notices**: the screenshot banner became `SimulatorPaneReducer.Notice` (icon, title, optional file to show in Finder) — screenshot and recording saved, memory warning sent, location set — shown for 6 s, one at a time
- **Run bar** (below the screen; `Run/`): a scheme menu and Run / Stop, building for the device the pane shows — Xcode's ⌘R without the debugger, in a terminal tab:
  - *Schemes* (`XcodeSchemeScanner`) come from the `.xcscheme` files (shared, and the user's `xcuserdata`) of the container and, for a workspace, of every project its `contents.xcworkspacedata` references — kept only when the `LaunchAction`'s `BuildableProductRunnable` is an `.app`. `xcodebuild -list` would list every framework and test scheme with nothing telling them apart: FlashScore's workspace has 96 schemes, 5 of which run the app (checked 2026-10-08). A container with no scheme files at all (XcodeGen without `schemes:`, schemes Xcode makes up per target) falls back to `xcodebuild -list -json`, unfiltered and with no product name. The project path is the repository's Xcode button's (`XcodeProjectButtonReducer.State.projectPath`), handed in by `TerminalPanelView`, and the scheme list reloads when it changes (`projectChanged`, its own action so the device polling's `.task` stays as it was). The choice is remembered per project *file name* (`simulatorRunSchemeByProject` in `UserDefaults`), so every worktree of a repository starts on the same scheme; without one, the scheme named after the workspace wins, else the first
  - *Running*: `runButtonTapped` writes `run-ios-app.sh` (`SimulatorRunCommand.script`) to `Application Support/<bundle id>/Scripts/` — rewritten on every run so it matches the app — and sends `delegate(.runRequested(command:title:))` with a short line that runs it (`/bin/bash <script> <project> <scheme> <product.app or ''> <udid> <device name>`, words single-quoted when needed). A shut-down device is booted at the same time, so it comes up while the app builds. The script: `xcodebuild … -destination 'platform=iOS Simulator,id=<udid>' build` (piped to `xcbeautify` when installed, else `-quiet`), then `-showBuildSettings -json` for where the app went (the entry whose `FULL_PRODUCT_NAME` is the product, or the first `.app` without one; else `BUILT_PRODUCTS_DIR` + product — an extension's scheme may not list the app it launches), `PlistBuddy` for its bundle id, `simctl bootstatus -b`, `simctl install`, `simctl launch --console-pty --terminate-running-process`. No `-derivedDataPath`: builds share Xcode's own derived data, so they are incremental with Xcode's. `simctl launch` passes Ctrl-C on to the app; a trap terminates it anyway. Failure and launch are posted with OSC 9, so a build left running in another tab notifies. Checked end to end on an XcodeGen sample (2026-10-08): build, install, launch, console output, Ctrl-C ending the app
  - *Stop* types Ctrl-C into the run tab (`TerminalViewStore.interrupt`), keeping its log; the panes live outside any store, so the panel does it through the view's `onStop` closure. Where the tab goes is RepositoryFeature's business (see its README)
