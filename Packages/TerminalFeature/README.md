# TerminalFeature

Embedded terminal (session, view, store).

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- SwiftTerm 1.99 (the step before 2.0) no longer hands out the view's `Terminal`, its `selection`, or the bytes the child writes, because output is now parsed on an IO thread. Everything goes through the view's copying, lock-taking API instead: `terminalDimensions`, `terminalStateSnapshot()` (the only read with the cursor; it copies every visible row), `visibleRowsText(_:)` for one row, `getBufferAsData()`, `keyboardEnhancementFlags`, `getSelection()`, `changeScrollback(_:)`. `LocalProcessTerminalView.dataReceived(slice:)` is still `open` but is no longer called. The child's output reaches the pane through `setProcessOutputHandler`, a byte-less callback on the IO thread. `ClaudeAwareTerminalView` coalesces it into one main-thread hop at a time (`PendingMainHop`), which drives the detector's foreground check and the startup command. Tests cannot set a selection range any more (`selectAll()` is the only setter), and output has to come from a real child to reach the handler. Following SwiftTerm's migration guide, text the app supplies goes in with `pasteText(_:)`, and `send` is kept for what stands in for typing (startup command, Ctrl-C, ⌥-arrow word motion). Dropped file paths are therefore pasted: bracketed when the program enabled bracketed paste.
- `TerminalSession`, `TerminalViewStore`, `TerminalContainerRepresentable` (in `TerminalViewRepresentable.swift`), `ClaudeAwareTerminalView`, `TerminalStatusDotView`
- Tests: `swift test` cannot build this package (SwiftTerm ships a Metal shader the SPM test build fails to compile; the app never enables Metal). Run them from `Packages/TerminalFeature` with `xcodebuild test -scheme TerminalFeature -destination 'platform=macOS' -skipMacroValidation -skipPackagePluginValidation` (add `-only-testing:TerminalFeatureTests/<Suite>` to narrow); without the two flags it stops on the unapproved TCA/CasePaths/Dependencies macros and on SwiftTerm's build-info plugin
- `TerminalContainerRepresentable` hosts every pane in one `TerminalPaneContainerView` and shows one at a time via `isHidden`. Only the visible pane is sized to the container (in its `layout()`, not in `updateNSView`, which can run before SwiftUI hands the container the new repository's width); hidden panes keep their last size, except that a pane never laid out is sized even while hidden. Pinning every pane to the container with constraints, as before, resized all of them whenever the container's width changed — and it changes with the repository on screen, whose simulator pane may be open while another's is not. Each resize is a reflow plus a SIGWINCH, and a narrow→wide reflow of a Claude Code screen joins unrelated lines until SwiftTerm clears soft-wrap flags on line feed (upstream PR migueldeicaza/SwiftTerm#745, unmerged as of 2026-10-09), so switching tabs between such repositories garbled every terminal a little more each time. Opening or closing the simulator still reflows the visible pane once
- `TerminalPaletteMapping` — `[NSColor]` → `[SwiftTerm.Color]` for `installColors`. The palette crosses the package boundary as `NSColor`, not as a Settings type, so TerminalFeature stays free of a Settings dependency (the same split the fg/bg colors already use); RepositoryFeature resolves the theme and passes the result down. SwiftTerm has no support for reading any theme file format — `Color.parse` handles X11 specs (`#rrggbb`, `rgb:r/g/b`) only, so the plist decoding lives in Settings. `installColors` derives all 256 colors from the 16 plus the terminal's background and foreground, so it must run *after* `nativeForegroundColor`/`nativeBackgroundColor` are set
- Killing a session must go through `TerminalViewStore.killSession` / `killSessions(notIn:)`, which hang up the shell with SIGHUP. Dropping the pane alone does not close the PTY (SwiftTerm leaves a read pending), and SwiftTerm's `terminate()` sends SIGTERM, which interactive zsh ignores. `RepositoryListView` calls `killSessions(notIn:)` whenever the session ids in state change, so reducer-side removals (worktree deletion) hang up too.
- `allowMouseReporting` is driven by the `terminalMouseReporting` setting (default on) and assigned in `TerminalContainerRepresentable.updateNSView`, not at creation, so panes pick up a change to the setting. Forcing it off breaks more than clicks: SwiftTerm's `scrollWheel` checks the flag *before* `terminal.mouseMode`, so a TUI on the alternate screen (lazygit, vim) gets the wheel as bare Up/Down arrow keys, which carry no coordinates — scrolling then always moves the focused pane instead of the one under the pointer. Text selection does not need the flag off; ⇧-drag bypasses reporting (`shiftBypassesMouseReporting`)
- `ClaudeAwareTerminalView` re-snaps the cell grid on `viewDidChangeBackingProperties` / `viewDidMoveToWindow` when the window's backing scale differs from the one the grid was measured for, by reassigning `font` (the only public entry to SwiftTerm's `resetFont`). SwiftTerm snaps cell width/height to the pixel grid of the screen current when the font is set and never re-measures on a screen change, so moving the window from an external monitor to the MacBook display (different scale) drew a stale grid: smeared glyphs, cell edges between pixels, wrong column count. Guarded on an actual scale change because the reassignment resizes the PTY (SIGWINCH) and clears the selection
- A pane's status comes only from the program's own OSC 7501 reports (the Program Status Protocol; Claude Code 2.1.295+, SwiftTerm 1.99+), whichever program sends them. A program probes with `OSC 7501 ; ?` and reports only if the terminal answers; SwiftTerm answers by itself and stores the records, and `ClaudeAwareTerminalView` overrides `LocalProcessTerminalView.programStatusChanged(source:records:)` (main thread, several updates possibly folded into one call). `TerminalProgramReport(records:)` takes the root record (no `id`), of any `app`: a program puts each subtask on a record of its own (Claude does for subagents and background tasks), and only the root says whether the user is wanted (a task still running after Claude's turn leaves the root `done`). `working` is active; `blocked` (dialogs: `kind` permission/question/auth), `done`, `idle` and `error` are waiting; no record is active — so a program that reports `idle` whenever it is at rest keeps its pane amber while it runs, which is what the protocol means. A change to waiting carries the `TerminalProgramReport` (the `app` name, the state in the package's own `State` — `blocked` with its `kind` — and `msg`, or `title` when the message is blank) up to RepositoryFeature for the notification; per the spec its text is cleaned for display outside the grid (format characters such as bidi overrides dropped, shortened to 300 characters). `notificationBody` words the state itself ("Claude needs your permission") and appends the program's message after a colon, so a notification reads the same for every program and the message is shown, as the spec asks, without meaning read into it. Claude clears its records on exit. Before 2026-10-09 the detector read the screen (`❯` prompt glyph, `❯ 1.` dialog options, a two-check WaitingStateGate) plus OSC 9;4 progress obtained by starting shells with `ConEmuANSI=ON`, with a Settings picker between them; all of that is gone, so an older Claude, Claude inside tmux (tmux does not answer the probe), or one with `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` set shows as active
- A report outlives a program that crashed or was suspended (Ctrl-Z) without clearing it, so once the pane has been quiet for 1.5 s after output, `ProgramStatusDetector.checkForeground()` sets the report aside while the pane's shell holds the foreground (`PtyForegroundProcess.isInForeground`: the shell leads its own process group, so the terminal's foreground group is the shell's pid exactly while no job runs; a foreground that can't be read leaves the report standing), and takes it up again when a program has it back — a Claude resumed with `fg` reports again only when its state changes. The records are left in SwiftTerm rather than cleared for the same reason. A shell that reported OSC 7501 itself would therefore never show
- `ClaudeAwareTerminalView` handles OSC 9 and OSC 777 desktop notifications the way Ghostty does (`TerminalNotification`, `OSC9Payload`), via `observeOscEvents`. SwiftTerm routes OSC 777 to a `notify` delegate method its Mac view leaves empty, and reads OSC 9 only as a progress report. The observation is passive — SwiftTerm still draws its own progress bar for `9;4` — and `OSC9Payload` ignores ConEmu's numbered subcommands (1–12) rather than showing them as a message. Events arrive on a SwiftTerm queue, in parse order, and are hopped to the main thread. A notification is only passed up (dropped once `ProgramStatusDetector.isStopped`, for a session being killed), marked `isFromStatusReportingProgram` while the detector has a report standing (`isReportStanding`: one made and not set aside as left behind) — Claude Code sends OSC 777 for the same moments it reports over OSC 7501 once its notification channel is Ghostty, and RepositoryFeature's `terminalNotificationSource` setting picks one of the two. A report rather than "has ever reported" (Wietty's rule), so a build in the same tab notifies again once Claude has exited and cleared its records. It does not move the pane's status, and neither does input — typing into Claude's input box leaves it `done` until the prompt is sent, and then Claude reports `working` itself. Until 2026-10-09 a notification held the pane at waiting until the next keystroke, for programs that notify without reporting status, which needed TerminalReply to tell SwiftTerm's own replies to the child (focus reports, `CSI 16 t` cell-size answers on every Claude focus change, the `OSC 7501 ; ?` answer) from typing on the shared `send(source:data:)` path. Both were removed: the shape-matching was fragile (it once released both panes on every tab switch) and a status of its own for a non-reporting program bought little over the notification itself
- ⌘-clicked links go through `ClaudeAwareTerminalView.requestOpenLink` (`open` on `LocalProcessTerminalView`) and `TerminalLinkTarget`, not SwiftTerm's default handler. SwiftTerm detects URLs and paths in plain output by itself (`linkReporting = .implicit`, highlighted while ⌘ is held), but its handler checks a path with `fileExists` as printed — relative to the *app's* working directory, `/` — so the relative paths Claude Code prints (a repository-relative path with a line, such as Packages/Foo/Bar.swift:12) opened nothing; and it reads a bare Bar.swift:12 as a URL with the scheme `Bar.swift`, which `NSWorkspace` silently fails to open. `TerminalLinkTarget` tries the text as a path first, whole and then without a `:line[:column]` suffix (keeping the line), in the shell's current directory and then at the repository root; only text that names no file becomes a URL. A file goes up through `onOpenFile` to RepositoryFeature, which opens it with ToolsIntegration's `FileOpener` (Xcode at the line for Swift, Android Studio for Kotlin, `open` otherwise); a link that resolves to nothing beeps. Claude Code itself prints plain text here, not OSC 8 hyperlinks: its `supports-hyperlinks` check finds no `TERM_PROGRAM` it knows (`FORCE_HYPERLINK=1` would override that)
- Find (⌘F, ⌘G/⇧⌘G, ⌘E) uses SwiftTerm's own find bar (search field, previous/next, case/regex/whole-word). SwiftTerm opens it only from Edit ▸ Find menu items, which this app does not have, and its show/hide functions are private. So `ClaudeAwareTerminalView.performFind` (reached through `TerminalViewStore.performFind(_:sessionId:)`) sends `performFindPanelAction(_:)` a menu item carrying the tag the real item would, taken from the `TerminalFindCommand`. ⌘F belongs to `RepositoryListView`'s always-registered filter shortcut, which decides at press time whether to open the active pane's find bar or focus the list's filter field. It is not handed off to the panel like ⌘T/⌘R, so its registration never changes — on macOS 27 a conditionally inserted shortcut can stop being delivered. ⌘G/⇧⌘G/⌘E sit beside the panel's zoom shortcuts. `ClaudeAwareTerminalView.requestFocus` leaves focus alone when it is already inside the pane: the representable calls it on every update pass, a Claude status change is one, and taking focus unconditionally pulled it out of the find field a moment after ⌘F, so the search text went to the shell
- ⌥←/⌥→ word motion is sent by `ClaudeAwareTerminalView` itself (a local `keyDown` monitor + `OptionArrowWordMotion`), because panes run with `optionAsMetaKey = false` (so Czech Option+4 = `$` works) and in that mode SwiftTerm drops it: legacy input becomes `moveWordLeft:`, which its `doCommand` doesn't handle (bash got nothing), and under the kitty protocol it sends a bare arrow with Option removed (Claude Code moved one character). Sends `ESC b`/`ESC f` normally and `CSI 1;3D`/`CSI 1;3C` when kitty flags are active. A monitor because SwiftTerm's `keyDown` is `public`, not `open`
- The global `terminalStartupCommand` setting (Settings → Terminal), or a repository group's own `RepoGroupSettings.terminalStartupCommand` when that is non-blank (a blank group command means "use the global one", not "none" — for "none", the group sets `skipGlobalTerminalStartupCommand`), rides on `TerminalSession.startupCommand` (trimmed, `nil` when blank) into the first built-in tab a repository opens. Tabs opened with + / ⌘T get it only when `terminalStartupCommandInNewTabs` is on (off by default — extra tabs are usually wanted as a plain shell); a retried tab gets it only if the tab it replaces had one. `ClaudeAwareTerminalView` types `TerminalSession.commandToType` — the startup command, or `claude --resume <id>` for a restored Claude tab — (plus `\r`) on the shell's **first output**, not right after `startProcess`: bytes written before the line editor is up are echoed by the tty as typeahead and then again at the prompt, so the command showed twice. It is typed, not passed as `zsh -c`, so it runs in the user's interactive shell, lands in history, and the shell stays open after it. External terminals (Terminal.app, iTerm, Warp) do not get it
- The font arrives already resolved (an `NSFont`, not a name and a size) and is assigned in the same place, but **only when the font name or point size actually differs** — compared field by field rather than with `!=`, which also weighs matrix and descriptor attributes the view may have derived — unlike the flags beside it. SwiftTerm's `font` setter rebuilds the bold/italic faces, calls `selectNone()`, and re-derives cols/rows from the new cell size in `resetFont()` — which resizes the PTY and SIGWINCHes the shell. That is correct for a deliberate zoom and wrong on every unrelated update pass, which is why the assignment is guarded
- Copy-on-select (`copiesSelectionAutomatically`, the `terminalCopyOnSelect` setting, off by default) copies the selection on `mouseUp`, after `super` has finished the gesture. `SelectionCopyDecider` holds the rules: nothing for a whitespace-only selection (an accidental drag across blank screen would wipe the pasteboard) or for the text it copied last; a gesture that selects nothing forgets that text, so highlighting it again copies again. Assigned in `updateNSView` like the mouse-reporting flag, since panes outlive a change to the setting
- `TerminalSession.title` is the terminal title the tab's program last set (OSC 0/2, or one popped with `CSI 23 t`), which `TerminalProcessDelegate.setTerminalTitle` passes up — SwiftTerm hops it to the main thread first — cleaned with `TerminalProgramReport.displayText` (control and format characters dropped, cut at 200 characters; an empty title reads as `nil`). `tabTitle` names the tab: `runTitle`, else `title`, else "Terminal N". Claude Code sets a short summary of the conversation, as plain text once the terminal has answered its OSC 7501 probe (otherwise prefixed with a `✳` glyph, animated `◐`/`◑` every 960 ms while it works); `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` turns it off. Nothing resets a title: Claude sets none on exit, so its summary stays on the tab until something else sets one, as in Ghostty and Terminal.app
- `TerminalSession.runTitle` marks a tab opened to run something (the simulator pane's Run) rather than as a shell; what that means for the tab bar and persistence is in RepositoryFeature's README. `TerminalViewStore.interrupt(sessionId:)` types Ctrl-C into a pane, which is how the pane's Stop reaches the run tab without killing it
- `TerminalViewStore(additionalEnvironment:)` adds `NAME=value` variables per session on top of `TerminalEnvironment`'s. The app passes the simulator MCP server's URL and the session's id (`BC_SIMULATOR_MCP_URL`, `BC_TERMINAL_SESSION_ID`, see `Packages/SimulatorFeature/README.md`); a closure rather than a dependency so this package stays free of SimulatorFeature. Like the rest of the environment it is fixed when the shell starts
