# DependencyGraphFeature

The module dependency graph sheet: a repository's KMP, Android and iOS modules as a layered graph, with the modules the current branch added or changed highlighted.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- `DependencyGraphReducer` / `DependencyGraphView` — the sheet. RepositoryFeature presents it from the row (the `dependencyGraph` row item, offered when the group supports Android or iOS) and from the terminal panel's "Modules" button. It reports nothing back: it only reads files and runs read-only git
- Nothing is evaluated. `GradleParser` and `TuistParser` read the build files as text, so a dependency added by a convention plugin, a loop or a variable is invisible. That trade buys an instant load with no Gradle daemon or Tuist run. The forms below are the ones a large KMP + Android + iOS (Tuist) repository used when this was written (2026-11-20); a repository with another layout shows what of it matches these forms
- **Gradle**: `settings.gradle(.kts)`'s `include(...)` calls (several paths per call, a space before the parenthesis) and `project(":x").projectDir = File(…, "dir")` / `file("dir")` remaps; other projects live at their default folder (":a:b" → `a/b`). An included path without a build file (an implicit parent like ":platform") is no module. Dependencies are `configuration(projects.a.b)` type-safe accessors (resolved through `GradleParser.accessor(forProjectPath:)`, Gradle's camel-casing at `-` and `_`, trying shorter chains) or `configuration(project(":a"))`. Only configurations ending in implementation/api/compileOnly/runtimeOnly/export/lintChecks/detektPlugins/ksp/kapt count, any flavour prefix included (`brandA_comImplementation`); that is what keeps `from(project(":baseline"))` out. Comments are stripped first, outside string literals
- A Gradle dependency is a test one when its configuration or any enclosing block's label contains "test" (`testImplementation`, `commonTest.dependencies {`, `getByName("androidDeviceTest")`). A block's label is the code before its `{` on that line, or the previous line when the brace stands alone. One pair declared both ways counts as regular (`DependencyGraph.deduplicated`)
- The module kind comes from the `plugins { }` block alone: a dependency like `projects.multiplatformSearch` would otherwise make an Android module KMP. KMP wins over Android, because KMP modules apply Android's KMP library plugin too. JVM modules (java-library, kotlin.jvm) sit in the Android tab
- **iOS (Tuist)**: the registry is every `static var X: Self { Self("X", kmpName: "y") }` under `extension FrameworkDependency where Self == Framework<SomeKind>` in `<ios>/Tuist/ProjectDescriptionHelpers`, where `<ios>` is the group's iOS subfolder, else `ios/`, else the root. Targets are `Target.<builder>(.Member, …)` calls of any builder name whose first argument is a registry member (or, for a builder with "Extension" in its name, an app extension): `internalDependencies: [...]` and `testsInternalDependencies: [...]` are its dependencies, bracket-balanced so arrays may span lines. A target whose list comes from a function (`TuistParser.listedDependencies`: a `func f(…) -> [any FrameworkDependency]` called from a body that binds `let x = Framework<Kind>.Member`) depends on what that function lists. Only registry members count, which drops external dependencies
- An iOS framework's folders are `<ios>/Frameworks/<name>` and, for one with a `kmpName`, `<folder>/ios`, where `<folder>` is the one Gradle module folder or parent of one that ends in the `kmpName` and holds an `ios/` folder (`DependencyGraphLoader.kmpFolders`; an ambiguous name matches nothing). No folder layout is hard-coded. Cross-platform edges: such a framework depends on the Gradle module sitting in `<folder>` (none when only its children are modules, like `resources/api`), and a framework with "Multiplatform" in its name on every Gradle module that `export(...)`s into the iOS framework (the umbrellas)
- `PlatformGraph` is what one tab draws: the platform's modules, the edges between them and, with "Other platforms" on, the other platforms' modules they depend on directly as dimmed, dashed boundary nodes whose own dependencies are not followed
- **Branch changes** (`DependencyGraphClient.loadChanges`): GitCore's `GitBranchChangesHelper` diffs the working tree against the merge-base with the default branch (`origin/<branch>`, else the local one; the group's configured default branch wins), adds untracked files, and lists which module folders existed at the merge-base (`existingFolders`). `ModuleChangeClassifier` gives each file to the module with the deepest folder containing it, so an iOS framework's `ios/` folder claims its files from the KMP module around it. A module none of whose folders existed at the merge-base is new; one that existed and owns a changed file is changed. Changes load only while highlighting is on
- `LayeredGraphLayout` is pure and computed in the reducer on every rebuild (under 10 ms for ~180 modules and ~1,000 edges, Debug build, measured 2026-11-20). Longest-path layers first (dependencies below; a cycle through test dependencies is broken where the walk meets it). Then `minimizingSpans` moves each module, within the room its edges leave, toward the side it has more essential edges on: with longest path alone every leaf sat in the bottom layer however high its users were. The other platforms' modules and modules with no edge in view get their own bands below the layers. Wide bands are dealt round-robin into rows so x still follows the order, then barycentre sweeps over the essential edges. Node widths are estimated from character counts at the canvas fonts, so the layout needs no text measuring
- `PlatformGraph.indirectEdges` are the edges a longer path already implies (a → c beside a → b → c), the complement of a transitive reduction over the edges pointing down the longest-path layers (a cycle keeps its upward edge, so no module is cut off). On a large repository (2026-11-20) they were 60 % of the KMP edges and most of those spanning four layers or more, the hairball. They are left out of the ordering and the drawing ("Indirect edges" draws them, a selected module always shows its own); the inspector still lists every direct dependency. Bands are striped, their labels drawn in view points so they stay at the left edge while panning
- `DependencyGraphCanvas` holds pan, zoom and hover and stacks `GraphDrawing` (everything in one `Canvas`, culled to the visible rect, edges batched into one path per style) under the input overlay. Pan and zoom are view `@State`, not reducer state. Input comes from `GraphInteractionLayer`, a transparent `NSView` overlay: SwiftUI has no scroll-wheel event on macOS. Click selects (and clears on empty space), drag or two-finger scroll pans, pinch or ⌘-scroll zooms around the pointer, and pointer moves feed the hover label. The view fits the graph whenever `layoutRevision` changes, and scrolls a module picked in the sidebar into view
- Text on the canvas is a deliberate exception to `scaledFont`: it is drawn at fixed graph sizes and scales with the zoom, like the boxes around it. Below 40 % zoom it is skipped. The sidebar, header and status bar use the scaled fonts
- The platform, "Highlight changes", "Other platforms", "Test dependencies" and "Indirect edges" choices are `@Shared(.appStorage)` (`DependencyGraphSharedKeys.swift`), so they carry across sheets and launches. A remembered platform the repository lacks falls back to the first one it has (`effectivePlatform`) without overwriting the setting
