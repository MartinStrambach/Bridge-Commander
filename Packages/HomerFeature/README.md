# HomerFeature

The Homer console section of the main window: sign-in, the process list and a process's page, the open questions, the other pages and the LangGraph workflow graphs of any number of Homer instances, natively; the rest (agent detail, file editor) as the web console's own page.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- Hybrid by design. The lists, a process's page and the sidebar's pages are native and poll the API; what is left (agent detail, the file editor, debug runs, the graph of a workflow whose server sends only Mermaid) opens the web console's page in a sheet (`HomerWebPageView`, SwiftUI `WebView`/`WebPage`), with "Open in Browser" beside it. The header's Safari button opens the current tab's page the same way
- The API and its JSON are mirrored from the Homer repo: `console/types/homer.ts` (models), `console/lib/api/client.ts` (calls), `app/SERVER.md` (endpoints, auth). Only the fields the lists show are decoded; unknown fields are ignored and unknown statuses decode as `.unknown`, so a newer server keeps working. Timestamps are Unix epoch **seconds**
- **Several instances, all signed in at once.** `HomerConsoleReducer` holds one `HomerInstanceReducer` per instance (`forEach`, so each one's effects and cancellation IDs are its own) and which one is on screen. Unlike the web console, which keeps one active instance and re-probes auth on every switch (`lib/instances/store.ts`, `instance-switcher.tsx`), every instance stays live: all check their session at launch and poll their open questions (the section switcher's badge is the sum; the instance menu shows each one's, and the others' total beside it), and the selected one alone polls its processes, Flow cells and agent names, only while the section is on screen (`activated`/`deactivated`). Switching shows the instance's last data at once and refetches right away. The header's instance menu lists them with ⌘1…⌘9 (hidden buttons do the switching, since a closed menu does not reliably answer its items' shortcuts; selecting the instance on screen again is a no-op, so the two never fight), adds one and removes the selected one. The processes/questions tab is the console's, not an instance's, so it survives a switch
- **Sign-in works like the web console's cookie mode** (`console/app/(auth)/login/page.tsx`, `lib/auth/auth-context.tsx`): `POST /api/v1/auth/login {username, password}` answers with an `HttpOnly` `homer_session` cookie (12 h by default), sent on every later call. No password is stored. Each instance's `start` probes `GET /api/v1/auth/me`: valid → signed in; 401 → its form. A 401 on any later call is an expired session: back to that instance's form with "Your session expired" (the menu says so too), the other instances unaffected. Login failures are told apart like the console does: 401 "Invalid credentials", 429 the login limiter (5/min per IP by default — the button stays off for 60 s, since retrying only prolongs the lockout), anything else the error itself. `HomerSignInReducer` is the form in both its roles: a signed-out instance's (its URL fixed) and "Add Instance" (the URL a field; cancellable unless there is no instance yet)
- **Fill from Passwords**: the form's fields carry `.username`/`.password` content types, but with no associated domain (Homer instances are any URL) macOS suggests nothing by itself — it shows its own "Passwords…" button only while the password field is focused. The button invokes the Edit ▸ AutoFill ▸ Passwords… item macOS adds to every app's Edit menu (`HomerPasswordAutoFill`, found by its action `_handleInsertFromPasswordsCommand:` since titles are localized; there is no public API for the picker). That picker inserts **one value into the focused field** — the login's username or password, by content type — and never its website, so the instance URL is always typed. To need one pick, each instance's last username is kept in `homerUsernames.json` (Application Support, by base URL; dropped on Remove) and fills its form; with the username empty, the button picks it first and opens the picker again for the password once a whole username lands (a single character is typing after dismissing the picker). If macOS drops the item, the button still focuses the field
- **Cookies are kept per instance, not by `URLSession`** (`HomerCookieJar`): `HTTPCookieStorage` matches cookies by host only — ports are ignored, and Homer's cookie has `Path=/` — so two instances on one host (`localhost:8080` and `:8081`, or two sub-paths) would sign each other out there. The session's `URLSession` neither stores nor sends cookies; `HomerAPI.send` adds the instance's jar as the `Cookie` header and feeds every `Set-Cookie` back (an already-expired one, as logout sends, removes). The jars persist to `homerSessions.json` in Application Support with `0600` permissions, so sessions survive a relaunch — the same trade `HTTPCookieStorage.shared` makes with its own file
- **One `URLSession` per instance** (`HomerAPI.session(for:)`): instances behind one Kubernetes ingress (`*.okubefs1.kube.lsoffice.cz`) share its IP and wildcard certificate, so a single session coalesces their HTTP/2 connections and sends one instance's requests over another's connection — the ingress answers those 421 Misdirected Request. Sessions never share connections
- Every request carries `X-Homer-CSRF: 1`: the backend's CSRF guard rejects cookie-authenticated requests without it (Homer ADR-0016)
- The instance list (`@Shared(.homerInstanceURLs)`, base URLs in the order added, which is the ⌘-digit order) gains an instance only on its first successful sign-in, so a failed attempt adds nothing; adding a URL already in the list signs that instance in again (a different user's data is dropped). Signing out keeps the instance in the list, signed out; "Remove" signs it out and forgets it. The selection is `@Shared(.homerSelectedInstance)`. `HomerEndpoint.normalize` accepts a URL pasted from the browser's address bar: it assumes `https`, drops a trailing console route (`/processes/123`, `/questions`, …) and any query, and keeps a sub-path otherwise. `displayName` keeps a port and sub-path, so two instances on one host read apart
- Polling follows the console's cadences: processes every 5 s and only for the instance on screen, open questions every 30 s for every signed-in instance. Each poll is one cancellable loop that fetches immediately; a filter change or "Load more" restarts it, so an answer for the old query never lands after the new one. "Load more" grows `limit` rather than paging, so the refresh keeps every loaded row current
- The process list is a SwiftUI `Table` with the console's columns (`process-table.tsx`): ID, Agent with tag chips, Status with the open-question count, Status Time, Last Command, Cost, Runner (pod-phase dot for Kubernetes runs), Flow (Root runs view only), Purge, Actions. Values use the console's own formats (`HomerFormat`, from `lib/utils/format.ts`): `dd.MM.yy HH:mm:ss`, `$0.0000`, "in 2d 3h". The page's filters are all there too: status chips, agent, sort order, tag chips (a row's tag adds itself), and "Children of #id" (context menu ▸ Show Child Runs), which overrides the Root runs view as in the console. "Total cost" sums the listed rows, not every match, like the console's
- Kill and Retry are offered only where the console offers them: by status (`isKillable`/`isRetryable`) and by the user's grants from `/auth/me` (`HomerUser.canKill`/`canRetry`, a port of `lib/auth/use-can.ts` — admin, owner `session:<username>`, or a grant whose agent pattern matches). The server checks again. Kill asks first; a retry opens the new run's page, as the console navigates to it
- The Flow cell (`HomerFlowSummary`, from `flow-summary-cell.tsx`) summarizes the runs under a root: a count from the page's `total`, cost and an aggregate state from the newest 100 (`partial` past that). Only the first 20 rows get one — one request per cell, polled every 30 s and restarted when those rows change — so "Load more" does not multiply the requests
- **The process page** (`HomerProcessDetailReducer`, from `processes/[id]/page.tsx`) is a sheet of the instance (`processDetail`), opened by `processTapped` from every page — the other pages ask through `HomerPageDelegate.openProcess`. It polls `GET /api/v1/status/{id}` every 5 s (the console refetches on its status stream instead) and drops an answer for a run no longer shown. A retry, a resume, a sub run's link or "Parent #id" shows the other run in the same sheet and pushes the current one on `backStack` (Back, ⌘[) — the console navigates. The run's open questions are the instance's, filtered by run and answered through it (`HomerQuestionCard` with the instance store); when the run's `openQuestions` count moves, the page tells the instance (`.questionsChanged`) to re-read them rather than wait out its 30 s poll. The sheet has a fixed ideal size and a plain stack: a height that followed the executions opening would make the sheet re-measure itself (AppUI's README). Switching instance or signing out closes it
- **LangGraph workflow**: `GET /processes/{id}/langgraph` without `graph` is the cheap probe (404 = no workflow), asked only when its answer is used — Resume (FAILED/KILLED/UNKNOWN runs, shown only with a workflow and a `run` grant), an expanded execution, or the running command's "Show workflow" — and asked again when a command runs that a "no workflow" answer did not see, since the workflow's artifact appears only when its command starts. The node states (`graph=true`) are polled every 5 s exactly while shown under the execution that ran the workflow or under the live command, whatever the run's status (a parked segment is FINISHED while its thread moves on). With a `topology` (Homer 1.28, ADR-0073) the workflow is drawn as its graph (see **Workflow graphs**): node boxes tinted by state, the sub runs' command dots along their bottom edge, the edges the run took green (`traversed`, Homer 1.29), and a node with sub runs opens them in a popover. Without one, or above the render cap, the nodes are the console's graph-less fallback list, in graph order (`HomerLangGraphStatus.nodes`: JSON object order does not survive decoding) — from `topology.nodes`, else from the deprecated `mermaid` source, which an older server or `homer_langgraph` runtime still sends alone (`draw_mermaid` writes nodes in graph order; ids are matched through langchain's `_to_safe_id` escaping) — drop the Mermaid path once no instance predates 1.28. The list has the legend's colors, the sub runs' command dots, and after each node the targets of the edges the run took from it. The subs list and node errors follow either. "Show Graph" (the run's console page over the sheet) is offered only for a Mermaid-only workflow, which the console can draw and this cannot
- **Command output** (`HomerProcessOutputReducer`, from `view-artifact-dialog.tsx`): `GET /api/v1/artifacts` once, then — while `X-File-Complete` is false — the log stream `GET /api/v1/stream/processes/{id}/logs?cmd=&stream=` with `Last-Event-ID` set to the bytes already read, so nothing is fetched twice (the console streams from byte 0 and swaps buffers). The server sends `log.chunk` with the new end offset as the event id and `{content}` as data, then `log.end`; a dropped connection resumes from the last offset with backoff. A chunk at or below the held offset is dropped. A running command's file 404s until its first byte, so for the live command a 404 means "wait for it". `HomerAPI.events` parses `text/event-stream` itself (`URLSession.bytes`, split on `\n`; `AsyncLineSequence` drops the blank lines that end an event). Appends happen in place on the state — copying the output out of the dictionary first would copy the whole log per chunk
- A Claude command's stdout is NDJSON (`--output-format stream-json`); `HomerClaudeTranscript` reads it as messages and tool calls (`claude-artifact-view.tsx`): Claude only if a `system` event carries `model` (hook events come first and do not), turns counted by distinct message id, tool results matched by `tool_use_id`, a trailing line kept until its newline arrives. It is parsed off the main actor for the first read and appended to per chunk. Shown in a `List` (rows recycle; a lazy stack would drive the sheet's size); raw text in an `NSTextView` (`HomerLogTextView`), which appends the new bytes instead of setting megabytes again and follows the end only while scrolled to it. The console's JSON tree mode is left out
- Downloads (an execution's output files, or any file from the Artifacts sheet, `GET /api/v1/artifacts/list`) go to `~/Downloads` under the file's name, numbered like a browser's when taken, and are shown in Finder — the app is not sandboxed. Artifact paths: an execution's `stdOut`/`stdErr` are absolute server paths, cut to the file name for the API (`toArtifactApiPath`); listed paths are relative and kept
- The web page sheet copies the instance's session cookies (`HomerClient.sessionCookies`) into the instance's own `WKWebsiteDataStore(forIdentifier:)` before loading, so the page opens signed in. The store's ID is derived from the base URL (`HomerEndpoint.webDataStoreID`, stable across launches), keeping instances apart there as the jars do; signing out also clears that store's cookies, which would otherwise stay valid until they expire. It loads the console as the top-level page: the console sends `X-Frame-Options: DENY` / `frame-ancestors 'none'`, which only an `<iframe>` would trip over. If the cookies are missing the console shows its own login page, which also works
- **The other pages** (Continuations, Schedules, Agents, Costs — the console's sidebar, Schedules and Costs for admins only) each have a reducer scoped into `HomerInstanceReducer` (`continuations`, `agents` — Schedules is the agents with a cron, so the two pages share it — `costs`). The console sets the instance's `page`; the instance tells the matching reducer `shown`/`hidden` (`syncShownChildPage`) — only while the instance is on screen and signed in, and never an admin-only page for anyone else — and the page polls only in between. A page asks the instance for what only it can do through `HomerPageDelegate`: `.unauthorized` (a 401 signs the instance out) and `.openWebConsole`. Signing out or another user signing in hides the page on screen and replaces every page's state. Each page adds its own calls to `HomerAPI` (an extension in its own file, through `HomerAPI.send`/`decode`) and its own `@DependencyClient`, rather than growing `HomerClient`. The header's Refresh reaches the page on screen as `refreshTapped`. `HomerAPI.send` takes request headers, pre-encoded query items, and `refusalsInServerWords` for calls whose 409/429 mean something other than a question or the login limiter (an agent run)
- **The pending continuations count** (the console's sidebar badge since Homer 1.31) is the instance's, not the page's: `GET /continuations?status=PENDING&limit=1`, whose `total` counts past the page, every 30 s. Unlike the questions, it is polled only while the instance is on screen — only the page picker's "Continuations (n)" shows it. A failure keeps the last count silently (the other polls report an expired session). A cancel on the page tells the instance (`HomerPageDelegate.continuationsChanged`) to re-read it at once
- **Continuations** (`HomerContinuationsReducer`, from `continuations/page.tsx`): the pending continuations, plus the ones that failed to fire (shown only when there are any — agents report crashes through continuations, so a lost one is a report nobody gets). Both lists come from one cancellable loop every 30 s, the console's cadence. Cancel is offered for PENDING only and is not checked against the user's grants: the console doesn't, and the API's continuation has no `owner` to check (the server applies `canControl`). A cancel always refetches, as the console does on settle; a 409 or 404 reads as "can no longer be cancelled", since the list was stale. A card's run numbers are links in one `AttributedString`, so the sentence wraps as text; they use a private `homer-process:<id>` scheme that the card's `openURL` action turns into `processTapped`
- **Agents and Schedules** (`HomerAgentsReducer`, one reducer for both) poll `GET /api/v1/agents` every 30 s while shown. The console keeps the list 5 min and refetches on the `/stream/agents` reload event; the poll stands in for that stream, as the process list's does for the status stream, and keeps the schedules' next and last runs current after a cron fires. Run, Edit, New Agent and Reload are offered by the user's grants (`HomerAgentPermissions.swift`, `can(action, agentName?)` from `use-can.ts`); unlike the console, Run needs a `run` grant and New Agent an `edit` grant on some pattern, since the server refuses anyone else. Agent detail, file editor, debug runs and "New agent" open in the web console; the agent's workflow graph is a sheet here (below). A schedule's Run (Homer 1.31, `POST /agents/{name}/cron-run`, admins only) fires the agent as its cron would, after the console's confirmation, whose wording matters: the call answers 204 even when a preflight (cost cap, cooldown, lock, parallel-run cap) starts nothing, and it returns no process id, so the new run is not opened — the list is refetched and the run shows up as the schedule's "Last run" (`lastRunProcessId`). A non-admin gets the 404 of an unknown agent, so the error names both causes
- **The Run sheet** (`HomerRunAgentReducer`) checks inputs as `lib/utils/validation.ts` does; typed inputs get only the required check, as there. It never sends an empty value: the console sends `""` for empty body and header inputs, which overrides the input's `default`. Query values are percent-encoded including `+`, which `URLComponents` would leave for the server to read as a space. The new run opens only after the sheet's `onDismiss` (`processToOpen` / `runSheetDismissed`): the run's page is a sheet too and cannot come up while the Run sheet is still going away
- **Costs** (`HomerCostsReducer`, admins only) runs three loops, so a month change restarts only one: the rolling-window snapshot every 5 s (`useCosts`' `refetchInterval`), and the month's and all-time ledgers every 30 s — the console only marks those stale after 30 s and re-reads them on mount or window focus, which a page left open never gets. `monthlyLoaded` carries the month it asked for and is dropped once another is picked. With no month picked the request has no `month` and the server answers with the current UTC month, so the page moves to the next month by itself, with no date logic in the app. While a picked month loads, the previous one stays on screen dimmed (the console's `keepPreviousData`). Usage bars follow `CostUsageBar`: green, yellow from 80 % of the cap, red at it; percentages round half up like `toFixed(0)`. The per-agent table lists agents that have spent or have a cap, so a capped agent with no spend shows at $0
- **Workflow graphs** (`HomerGraphLayout`, `HomerWorkflowGraphView`, from `workflow-graph.tsx` and `lib/langgraph/layout.ts`). The console lays a `topology` out with dagre; there is no Swift dagre, so `HomerGraphLayout` is a native layered layout that follows dagre's conventions step by step, so the two look alike: DFS cycle breaking (reversed edges drawn the right way round), every edge spanning two ranks with its label in the odd rank between (dagre's doubled `minlen`/halved `ranksep`), longest-path ranks then moves that shorten edges (standing in for network simplex — the factory graph gets dagre's height), dummy chains, dagre's ordering loop (up sweep first, ties biased right every other two sweeps, an equally good order replacing the best, four sweeps without gain to stop — that tie rule is what spreads long edges to both sides of a chain), and Brandes–Köpf x positions. A weighted least-squares placement was tried first and dropped: layer-by-layer sweeps cannot move a long edge's dummy column as one, so chains drifted into a staircase. Self-loops, the 200-node/300-edge cap, the 40-character label cut and the spacings (`nodesep` 32, `ranksep` 44, `edgesep` 16) are `layout.ts`'s. Boxes are measured with the font they are drawn in (callout × `uiFontScale`), not estimated per character, so the layout follows the text size; it is computed off the main actor and only when the topology or scale changes, not on every 5 s status poll. Edges are a `Canvas`; nodes are views over it, for tooltips, popovers and accessibility. On the process page the graph is at most 480 pt high and scrolls inside, keeping the sheet's height fixed. "Export" (and the graph's context menu) saves or copies the whole graph as a PNG: `HomerWorkflowGraphDrawing` — the edges and boxes alone, which the screen shows with clear popover buttons laid over it, as the console lays its triggers over the SVG — rendered by `ImageRenderer` at 2× in the current appearance and text size, the bitmap's point size set so it opens at the graph's size
- **An agent's graphs** (`HomerAgentWorkflowGraphReducer`, the console's `workflow-graph-card.tsx`): `GET /api/v1/agents/{name}/langgraph` gives one entry per LangGraph command, a `topology` or an `error` (`busy` when too many inspections run); `200 []` means none. The server runs `homer_langgraph inspect` in a subprocess per call, and the agent list says nothing of which agents have one, so it is asked only when the sheet opens (card button or context menu) and on Refresh, never polled. Shown as structure only — no run, so no tints. The sheet is resizable: a flexible frame alone left its window fixed, `.presentationSizing(.fitted)` makes it resizable from the content's minimum, opening at the ideal size (checked 2026-10-08)
- Question text is Markdown written by an agent. It is rendered inline-only (`AttributedString`, `.inlineOnlyPreservingWhitespace`), and `Text` never loads images — the console renders only an image's alt text for the same reason: an agent-supplied image URL would otherwise beacon on view
- Tests: `.dependencies` (DependenciesTestSupport) gives each test its own app storage for the `@Shared` instance list and selection. A `@Shared` value written by a delegate action that a `.send` delivers within the same effect is already the new one at the step before it, so its expectation goes there (see `addInstance` in `HomerConsoleReducerTests`). Build a `State` before passing it to `TestStore`, never inline: `initialState` is an autoclosure evaluated inside the store's own dependencies, so a `@Shared` value written there lands in a different app storage than the one the store's expectations read, and the URL shows up as a spurious `""` → URL diff
