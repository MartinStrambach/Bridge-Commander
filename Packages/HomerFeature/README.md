# HomerFeature

The Homer console section of the main window: sign-in, the process list and the open questions of any number of Homer instances, natively; everything else as the web console's own page.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- Hybrid by design. The lists (`HomerProcessListView`, `HomerQuestionListView`) are native and poll the API; a process's detail (logs, artifacts, workflow graph, kill/retry) opens the web console's page in a sheet (`HomerWebPageView`, SwiftUI `WebView`/`WebPage`), with "Open in Browser" beside it. The header's Safari button opens the current tab's page the same way
- The API and its JSON are mirrored from the Homer repo: `console/types/homer.ts` (models), `console/lib/api/client.ts` (calls), `app/SERVER.md` (endpoints, auth). Only the fields the lists show are decoded; unknown fields are ignored and unknown statuses decode as `.unknown`, so a newer server keeps working. Timestamps are Unix epoch **seconds**
- **Several instances, all signed in at once.** `HomerConsoleReducer` holds one `HomerInstanceReducer` per instance (`forEach`, so each one's effects and cancellation IDs are its own) and which one is on screen. Unlike the web console, which keeps one active instance and re-probes auth on every switch (`lib/instances/store.ts`, `instance-switcher.tsx`), every instance stays live: all check their session at launch and poll their open questions (the section switcher's badge is the sum; the instance menu shows each one's, and the others' total beside it), and the selected one alone polls its processes, Flow cells and agent names, only while the section is on screen (`activated`/`deactivated`). Switching shows the instance's last data at once and refetches right away. The header's instance menu lists them with ⌘1…⌘9 (hidden buttons do the switching, since a closed menu does not reliably answer its items' shortcuts; selecting the instance on screen again is a no-op, so the two never fight), adds one and removes the selected one. The processes/questions tab is the console's, not an instance's, so it survives a switch
- **Sign-in works like the web console's cookie mode** (`console/app/(auth)/login/page.tsx`, `lib/auth/auth-context.tsx`): `POST /api/v1/auth/login {username, password}` answers with an `HttpOnly` `homer_session` cookie (12 h by default), sent on every later call. No password is stored. Each instance's `start` probes `GET /api/v1/auth/me`: valid → signed in; 401 → its form. A 401 on any later call is an expired session: back to that instance's form with "Your session expired" (the menu says so too), the other instances unaffected. Login failures are told apart like the console does: 401 "Invalid credentials", 429 the login limiter (5/min per IP by default — the button stays off for 60 s, since retrying only prolongs the lockout), anything else the error itself. `HomerSignInReducer` is the form in both its roles: a signed-out instance's (its URL fixed) and "Add Instance" (the URL a field; cancellable unless there is no instance yet)
- **Cookies are kept per instance, not by `URLSession`** (`HomerCookieJar`): `HTTPCookieStorage` matches cookies by host only — ports are ignored, and Homer's cookie has `Path=/` — so two instances on one host (`localhost:8080` and `:8081`, or two sub-paths) would sign each other out there. The session's `URLSession` neither stores nor sends cookies; `HomerAPI.send` adds the instance's jar as the `Cookie` header and feeds every `Set-Cookie` back (an already-expired one, as logout sends, removes). The jars persist to `homerSessions.json` in Application Support with `0600` permissions, so sessions survive a relaunch — the same trade `HTTPCookieStorage.shared` makes with its own file
- Every request carries `X-Homer-CSRF: 1`: the backend's CSRF guard rejects cookie-authenticated requests without it (Homer ADR-0016)
- The instance list (`@Shared(.homerInstanceURLs)`, base URLs in the order added, which is the ⌘-digit order) gains an instance only on its first successful sign-in, so a failed attempt adds nothing; adding a URL already in the list signs that instance in again (a different user's data is dropped). Signing out keeps the instance in the list, signed out; "Remove" signs it out and forgets it. The selection is `@Shared(.homerSelectedInstance)`. `HomerEndpoint.normalize` accepts a URL pasted from the browser's address bar: it assumes `https`, drops a trailing console route (`/processes/123`, `/questions`, …) and any query, and keeps a sub-path otherwise. `displayName` keeps a port and sub-path, so two instances on one host read apart
- Polling follows the console's cadences: processes every 5 s and only for the instance on screen, open questions every 30 s for every signed-in instance. Each poll is one cancellable loop that fetches immediately; a filter change or "Load more" restarts it, so an answer for the old query never lands after the new one. "Load more" grows `limit` rather than paging, so the refresh keeps every loaded row current
- The process list is a SwiftUI `Table` with the console's columns (`process-table.tsx`): ID, Agent with tag chips, Status with the open-question count, Status Time, Last Command, Cost, Runner (pod-phase dot for Kubernetes runs), Flow (Root runs view only), Purge, Actions. Values use the console's own formats (`HomerFormat`, from `lib/utils/format.ts`): `dd.MM.yy HH:mm:ss`, `$0.0000`, "in 2d 3h". The page's filters are all there too: status chips, agent, sort order, tag chips (a row's tag adds itself), and "Children of #id" (context menu ▸ Show Child Runs), which overrides the Root runs view as in the console. "Total cost" sums the listed rows, not every match, like the console's
- Kill and Retry are offered only where the console offers them: by status (`isKillable`/`isRetryable`) and by the user's grants from `/auth/me` (`HomerUser.canKill`/`canRetry`, a port of `lib/auth/use-can.ts` — admin, owner `session:<username>`, or a grant whose agent pattern matches). The server checks again. Kill asks first; a retry opens the new run's page, as the console navigates to it
- The Flow cell (`HomerFlowSummary`, from `flow-summary-cell.tsx`) summarizes the runs under a root: a count from the page's `total`, cost and an aggregate state from the newest 100 (`partial` past that). Only the first 20 rows get one — one request per cell, polled every 30 s and restarted when those rows change — so "Load more" does not multiply the requests
- The web page sheet copies the instance's session cookies (`HomerClient.sessionCookies`) into the instance's own `WKWebsiteDataStore(forIdentifier:)` before loading, so the page opens signed in. The store's ID is derived from the base URL (`HomerEndpoint.webDataStoreID`, stable across launches), keeping instances apart there as the jars do; signing out also clears that store's cookies, which would otherwise stay valid until they expire. It loads the console as the top-level page: the console sends `X-Frame-Options: DENY` / `frame-ancestors 'none'`, which only an `<iframe>` would trip over. If the cookies are missing the console shows its own login page, which also works
- Question text is Markdown written by an agent. It is rendered inline-only (`AttributedString`, `.inlineOnlyPreservingWhitespace`), and `Text` never loads images — the console renders only an image's alt text for the same reason: an agent-supplied image URL would otherwise beacon on view
- Tests: `.dependencies` (DependenciesTestSupport) gives each test its own app storage for the `@Shared` instance list and selection. A `@Shared` value written by a delegate action that a `.send` delivers within the same effect is already the new one at the step before it, so its expectation goes there (see `addInstance` in `HomerConsoleReducerTests`). Build a `State` before passing it to `TestStore`, never inline: `initialState` is an autoclosure evaluated inside the store's own dependencies, so a `@Shared` value written there lands in a different app storage than the one the store's expectations read, and the URL shows up as a spurious `""` → URL diff
