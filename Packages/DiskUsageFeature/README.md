# DiskUsageFeature

The Disk section: a DaisyDisk-style dashboard that scans a volume or folder, shows where the space goes as a sunburst, and removes what is not wanted.

Design notes and gotchas for this package. Project-wide conventions are in the root `CLAUDE.md`.

## Notes

- `DiskUsageReducer` / `DiskUsageView` — the section. `RootRepositoryView` (RepositoryFeature) creates the store with the window and shows the view for `AppSection.disk`, handing it the section switcher as the header's leading view like the Homer console. The view is unmounted while another section is on screen but the store is not, so a scan started here keeps running and the result is there when the section comes back
- `DiskScanner` builds a `DiskNode` tree the way `du` counts (allocated blocks, hard links once across the whole scan, symbolic links not followed, mount points not entered), reading each directory with `getattrlistbulk` as ToolsIntegration's `DerivedDataUsageScanner` does. Unlike that scanner it parses each entry by the attributes reported as returned rather than at fixed offsets (no `FSOPT_PACK_INVAL_ATTRS`), so a file system that cannot report an attribute is told from one reporting zero. The folders still to be read wait in one last-in-first-out `ScanWorkQueue` that `workerCount` (16) threads take from, so every worker stays busy until the end however lopsided the tree; a fan-out fixed at the top two levels left one worker with most of a volume. Threads, not tasks: a worker is blocked in the kernel nearly all the time (sampled: 4% user time), and sixteen blocked tasks would crowd out the cooperative pool. The tree is assembled from the bottom as folders finish in any order: a `FolderInProgress` holds what its folder was read to contain and how many subfolders are still to finish, and becomes a `DiskNode` with the last one. A folder's descriptor stays open until each subfolder has been opened from it with `openat`; with the LIFO queue a worker goes deep before wide, so open descriptors stay around the tree's depth per worker (a GUI app's soft limit is 256). Opening a folder costs the kernel more than reading it, so a folder whose parent reports `ATTR_DIR_ENTRYCOUNT` 0 is a node without being opened: 64% of the 1.7 million folders under `~/Library/Developer` are empty. The exception is a firmlink (`ATTR_CMN_FLAGS` has `SF_FIRMLINK`): the sealed system volume reports `/Users`, `/Applications`, `/Library`, `/private`, `/opt`, `/Volumes`, `/usr/local` and a few under `/System/Library` as empty folders that are no mount point, so a scan of `/` that trusted the count stopped at the 13 GB of the system volume and never saw the data volume (2026-10-16). A firmlink is read like any folder; `openat` through it lands on the data volume. Its own mount point, `/System/Volumes/Data`, is skipped as a mount point, so nothing is counted twice. Measured there on 3.9 million items / 317 GB, warm: 71 s with the fixed fan-out, 32 s with the queue, 17 s skipping empty folders (8 and 32 workers were within 10% of 16); the total matched `du -sk` to the byte (2026-10-16). `DiskScannerBenchmark` repeats the measurement for the folder in `DISK_SCAN_BENCHMARK_ROOT`. A folder keeps nodes for its `filesKeptPerDirectory` (100) largest files and sums the rest into one `DiskNode.Kind.smallerFiles` entry: a whole volume has millions of files, and a node each would cost more memory than the chart could show. A folder that cannot be opened or read is a node with `isInaccessible` set and size 0, and counts toward `DiskScanResult.inaccessibleFolders`; the result's footer then offers the Full Disk Access pane. Progress (`DiskScanProgress`) is sampled from a shared `ScanTally` every 150 ms by a reporter task, not pushed per entry
- `DiskNode` is an immutable class compared by identity. The tree is never copied: the reducer keeps `path`, the chain from the scan root to the folder on screen, and a deletion rebuilds only that chain (`DiskTree.removing(childNamed:from:)`), so the rest of the tree is shared with the previous state. Nodes carry no parent pointer and no full path — only the root's `name` is a path — so a location is told from a chain (`DiskTree.url(of:)`), and a chart segment carries its `ancestry` from the centre's child down
- `SunburstLayout` lays the centre node's descendants out in up to six rings as fractions of a turn, largest first clockwise from the top; children thinner than `minimumSpan` are summed into a trailing grey `rest` segment, and only children at least `minimumSpanToDescend` wide are laid out further. A segment's hue is its midpoint on the circle, so neighbours shade into one another and a folder's children stay in its colour range. `SunburstChartView` draws it in a `Canvas` with hit testing in polar coordinates: clicking a first-ring folder opens it, clicking deeper selects its first-ring ancestor, clicking the centre goes up. The mouse's back button, anywhere in the window (AppUI's `onMouseBackButton`, on the result view), goes Back through the history like ⌘[, as a browser's does; it went up before the history existed. A change of centre is animated the way DaisyDisk zooms: `SunburstTransition` gives every segment of the old and the new layout a frame in both (an opened folder's arc grows to the whole circle while sliding under the centre, its contents move one ring in and spread out, its siblings collapse onto the top seam; going up is the reverse; a deletion keeps arcs in place and fades the removed one while its neighbours slide over it), and the chart's `Animatable` canvas interpolates between them, clipped to the ring band. Its animatable value is a phase that only ever grows, one unit per transition: an animatable value is interpolated from what was last drawn, so resetting a progress to 0 and animating it to 1 in one update would not move. A folder opened from the list that was too thin to be drawn zooms out of its parent's `rest` arc. Reduce Motion skips the animation. Hover is `@State` shared between the chart and the list (`DiskChildrenList`), never a store action: one per mouse move would wake every view bound to the store
- Keyboard, as DaisyDisk's map: ↑/↓ select (⌥↑/⌥↓ or Home/End the first and last), Return, → or ⌘↓ open, ← or ⌘↑ go up, Space shows the selection in Quick Look, Escape clears the selection — `DiskKeyboard` maps them, from an `onKeyPress` on the result view, which is `focusable` and takes focus on appear and on any click inside it (a simultaneous tap gesture, so rows and segments still get theirs). ⌘[ ⌘] ⌘R ⌘⌫ ⌥⌘⌫ are not there but `keyboardShortcut`s of the Back/Forward, Rescan, Move to Trash and Delete buttons, so they work whatever holds focus; ⌘R is free because the repository list is `.disabled` under this section. Back and Forward walk `backHistory` / `forwardHistory`, every move but those two pushing the folder left and clearing Forward. An entry is the folder's names below the scan root, not its nodes: a deletion rebuilds the chain, and kept nodes would show the removed item again. An entry is resolved against the current tree, stopping at the last folder still there, and one that resolves to the folder on screen is skipped. A move up, by any route, selects the folder just left, so ↓/Return carry on from it. The list scrolls to the selection (`ScrollViewReader`), since the arrow keys can move it off screen
- Quick Look (Space, or the row's context menu) is SwiftUI's `quickLookPreview` on the result view, bound to `selectedURL` while `isQuickLookShown`, with the folder's on-disk items as the panel's collection: the panel's own arrow keys then move through them, and `quickLookItemChanged` makes the selection here follow (the panel is the key window while open, so the map's keys do not reach the result view). The flag is reducer state rather than `@State` so Space goes through `DiskKeyboard` like every other key and the rule is in one place: it is only ever set with a selection, every move or deletion that clears the selection clears it too, and a change of folder closes the panel, which was showing an item of the folder left. A held Space is ignored on repeat; each repeat would toggle the panel
- Selection is `selectedNames`, the folder's children in the order they were selected: the last is the lead (what Quick Look shows, where ↑/↓ move from, `selectedName`) and the first the anchor. A plain click or ↑/↓ selects one; ⌘-click (`selectionToggled`) adds or removes; ⇧-click or ⇧↑/⇧↓ (`selectionExtended`, `selectionMoved(_:extending:)`) selects from the anchor to the item in the list's order so the item becomes the lead, as Finder does; ⌘A selects everything. The list and the chart read the click's modifiers from `NSEvent.modifierFlags` in their tap handlers; SwiftUI's tap gesture does not carry them. The chart highlights every selected first-ring arc; the footer names one item, or "N items selected" with their total (`DiskNodeDescription.summary(of:within:)` for several)
- Removal goes through `DiskUsageClient`: Move to Trash (`FileManager.trashItem`, reversible; the space is freed when the Trash is emptied) or Delete Permanently (`removeItem`), both after one alert naming the item and its size, or the count and total of a selection, both recorded in the activity log. The selected items are removed one after another (`deletingNames`), each subtracted from the tree as it goes, and the failures reported together at the end (`removalFailures`, `removalFinished`) rather than one alert over another. The summed smaller files, the hidden space and unreadable folders cannot be removed (`DiskNode.isRemovable`), nor can what DaisyDisk also refuses: the folders macOS is made of, the home folder and its `Library`, any mounted volume's root, and the scan root (`DiskProtectedLocations`, `State.canRemove`): the delete button is permanent, and a stray ⌥⌘⌫ on `/Library` would be the end of the system. The buttons are disabled with the reason in their tooltip, a protected item in a selection is left out, and the reducer checks again on confirmation. Rescan repeats the last scan from its root (`lastScanRoot`, kept when the result is left for the picker)
- Leaving the result for the picker (the header's "Scan another volume or folder", `newScanTapped`) keeps it in `lastResult` with the folder on screen as names below the root (`lastResultPath`), and the picker's "Last scan" card reopens it where it was (`lastResultReopened`) without scanning again; the card shows the root's size and how long ago the scan finished (`DiskScanResult.finishedAt`, set by the scanner), since the tree is the disk as it was then. The kept result is replaced only when another scan finishes, so a scan stopped or failed from the picker still leaves the old one to reopen
- A scan of a volume reports less than Finder: purgeable space (local snapshots and caches the system frees on demand, where deleted bytes often go first — "I emptied DerivedData and got nothing back"), the other volumes of the APFS container (VM, Preboot, Update, Recovery on the startup disk), unreadable folders and file system data are allocated but not in the tree. `DiskVolumeLister.usage(ofVolumeAt:)` measures them as the scan finishes (`DiskScanResult.volume`): the allocation is the capacity less the plain free space (`volumeAvailableCapacityKey`), purgeable the difference between that and the free space for important usage, and the sibling volumes (same capacity and free space, hidden ones included, the Data volume excepted for `/` since firmlinks put it in the scan) each by their own `statfs` blocks. The reducer adds the difference to the root as one `DiskNode.Kind.hiddenSpace` child, DaisyDisk's "hidden space", so the centre adds up to Finder's used figure; it is grey in the chart, nowhere on disk, not removable, and its breakdown is in the footer. A folder scan has none
- Starred folders (`diskStarredFolders`, a `fileStorage` shared key of `DiskLocation` keys, most recent last) are pinned to the picker under the volumes: the header's star pins or unpins the folder on screen, the picker's card scans it or takes it off. `DiskLocation.key(for:)` is the one spelling of a path (standardized, no trailing slash) that the starred list, the protected list and the scan root are compared by
